## 一、测试总览

### 1.1 测试原则

1. **黑盒测试原则**：纯玩家视角，不知道代码实现，发现的问题更真实
2. **最小单元化原则**：一次只测一个系统，用对应存档直接开始
3. **并行测试原则**：多个Agent同时测不同内容，效率翻倍
4. **回归测试原则**：每次发布前都要跑一遍核心测试用例

### 1.2 测试流程

```
开发完成 → 开发者自测 → 黑盒测试 → Bug修复 → 回归测试 → 发布
```

## 二、测试存档体系

### 2.1 为什么需要测试存档

**传统测试的问题**：
- 从头玩太慢，浪费时间
- 测不到后期内容，覆盖率低
- 难以精确复现bug
- 难以单独测试某个系统

**测试存档的优势**：
- 秒级启动，直接从特定进度开始
- 全覆盖，每个系统每个阶段都有对应存档
- 精确复现，bug复现100%成功
- 单元化测试，想测什么就测什么
- 并行测试，多个Agent同时从不同存档开始

### 2.2 存档命名规范

```
save_{编号}_{阶段描述}.json
```

示例：
- `save_01_newbie_lvl1.json` - 新手阶段，1级
- `save_02_early_lvl3.json` - 游戏初期，3级
- `save_03_mid_lvl5.json` - 游戏中期，5级

### 2.3 标准测试存档清单

## 三、最小单元化测试方法

### 3.1 什么是最小单元化测试

把游戏拆成一个个独立的测试单元，每个单元只测一个特定功能或场景，用对应的存档直接开始测试。

**核心原则**：
- 一次只测一个东西
- 用对应存档直接开始
- 测完就结束，不用继续玩
- 黑盒状态，纯玩家视角

### 3.2 测试单元划分

#### 按系统划分
1. **角色系统单元**：属性、等级、技能、觉醒
2. **战斗系统单元**：普通攻击、技能、状态、逃跑、元素克制
3. **任务系统单元**：接取、进度、完成、奖励、任务链
4. **地图系统单元**：移动、解锁、地点行动、NPC分布
5. **背包系统单元**：物品、使用、装备、数量
6. **商店系统单元**：购买、出售、价格、声望折扣
7. **日常系统单元**：签到、每日任务、刷新
8. **大事件单元**：触发、推进、分支、结局
9. **存档系统单元**：保存、读取、版本迁移
10. **UI界面单元**：各面板、按钮、显示、响应

#### 按阶段划分
1. **新手阶段（1-2级）**：角色创建、新手引导、基础操作
2. **初期阶段（3-4级）**：基础玩法、第一个任务、第一次战斗
3. **中期阶段（5-7级）**：多个系统、日常、探索
4. **后期阶段（8级+）**：大事件、高阶技能、复杂系统

### 3.3 测试步骤

1. **选择测试单元**：确定要测哪个系统
2. **选择对应存档**：找到最适合的测试存档
3. **加载存档**：用存档管理工具导入，或游戏内读取
4. **执行测试用例**：按照测试用例一步步测
5. **记录问题**：发现bug详细记录（步骤、预期、实际）
6. **测试总结**：给出测试结论（通过/不通过）

## 四、多Agent并行黑盒测试方法论

### 4.1 核心思路

**为什么用多Agent并行测试**：
- 开发者自己测，容易陷入思维定式，测不出自己写的bug
- 单人测试速度慢，覆盖不全
- 从开发者视角测，不是从玩家视角测

**多Agent黑盒测试的优势**：
- 纯玩家视角，不知道代码实现，发现的问题更真实
- 并行测试，多个Agent同时测不同内容，效率翻倍
- 7x24小时不间断，不知疲倦
- 每个Agent都是独立的，不会互相影响
- 测试过程详细记录，每一步操作都有日志

### 4.2 黑盒测试原则

**绝对不能告诉Agent的信息**：
- ❌ 代码实现细节
- ❌ 修复了什么bug
- ❌ 新增了什么功能
- ❌ 数值公式
- ❌ 设计思路
- ❌ 任何内部信息

**只告诉Agent的信息**：
- ✅ 这是个什么游戏
- ✅ 基本操作方式
- ✅ 你的任务是玩游戏，找bug，记录体验
- ✅ 发现任何不对劲的地方都记录下来

**为什么要纯黑盒**：
- 玩家不知道代码怎么写的，他们遇到问题就是真问题
- 如果告诉Agent"我修了XXbug"，Agent会特意去测那个点，而不是自然游玩中发现
- 黑盒发现的bug优先级更高，因为真实玩家也会遇到

### 4.3 多Agent分工策略

#### 按测试方向分工

建议同时开 3-5 个Agent，每个负责不同方向：

| Agent角色 | 测试重点 | 目标 | 对应存档 |
|-----------|----------|------|---------|
| **新手体验官** | 从零开始，完整体验新手流程 | 发现新手引导问题、前期bug、入门难度问题 | save_01_newbie_lvl1 |
| **战斗狂人** | 专注战斗系统，打各种怪，试各种技能 | 发现战斗bug、平衡问题、技能bug | save_05_battle_test |
| **探索家** | 跑遍所有地图，做所有任务，和所有NPC对话 | 发现内容bug、任务bug、NPC对话bug | save_03_mid_lvl5 |
| **经济学者** | 专注商店、装备、强化、赚钱、花钱 | 发现经济系统bug、数值平衡问题 | save_06_economy_test |
| **极限测试员** | 故意作死，试各种边界情况 | 发现崩溃bug、异常状态、边界条件问题 | save_04_pre_disaster |

#### 按进度分工

也可以按游戏进度分工：

| Agent | 游戏阶段 | 测试重点 | 对应存档 |
|-------|----------|----------|---------|
| Agent A | 前期（1-5级） | 新手体验、前期平衡、入门引导 | save_01 + save_02 |
| Agent B | 中期（5-10级） | 中期系统、装备、技能、任务 | save_03 + save_05 |
| Agent C | 后期（10级+） | 后期内容、大事件、高级系统 | save_04 |

#### 并行数量建议

- **最少2个**：一个测新手，一个测深度
- **推荐3-4个**：覆盖主要玩法方向
- **最多5-6个**：太多了bug反馈处理不过来
- **不要超过8个**：边际效益递减，管理成本上升

### 4.4 Agent测试指令模板

```
你是一个游戏测试员，负责测试《全职法师》网页游戏。

## 你的任务

- 测试完给出总结：发现了哪些问题，整体体验如何

## 测试重点
```

## 七、Bug报告规范

### 7.1 Bug报告模板

```
【Bug标题】简短描述bug

【严重程度】致命/严重/一般/轻微/体验

【复现步骤】
1. 第一步...
2. 第二步...
3. 第三步...

【预期结果】
应该发生什么

【实际结果】
实际发生了什么

【测试环境】
- 浏览器：Chrome/Firefox/...
- 版本：v0.x.x
- 测试存档：save_xx_xxx

【附加信息】
截图、日志等（如有）
```

### 7.2 严重程度分级

| 级别 | 定义 | 示例 |
|------|------|------|
| **致命** | 游戏无法运行，或核心功能完全不可用 | 白屏、进不去游戏、战斗卡死 |
| **严重** | 主要功能不可用，或数据丢失 | 存档损坏、任务无法完成、重要物品消失 |
| **一般** | 某个功能有问题，但有 workaround | 某个按钮点不了、显示错误、数值不对 |
| **轻微** | 小问题，不影响正常游戏 | 错别字、对齐问题、颜色不对 |
| **体验** | 不是bug，但体验不好 | 操作麻烦、提示不清楚、流程繁琐 |

## 八、测试经验沉淀

### 8.1 常见Bug模式

#### Bug模式1：对象/数组类型混淆
**现象**：调用数组方法（如sort、map、filter）时报错"xxx不是函数"
**原因**：数据是对象{}而不是数组[]
**易发位置**：getAllXxx() 类方法返回值
**预防方法**：
- 使用 `Object.values()` 将对象转为数组
- 调用数组方法前先确认类型
- 统一数据返回格式（尽量统一返回数组）

**历史案例**：
- 妖魔图鉴 enemies.sort 报错 → 修复：`Object.values(DataManager.getAllEnemies())`

#### Bug模式2：事件监听器泄漏
**现象**：界面完全无法点击，所有按钮都没反应
**原因**：全局事件监听器没有被正确移除，持续拦截所有事件
**易发位置**：弹窗/消息系统的全局点击拦截
**预防方法**：
- 使用闭包保存监听器引用，不要依赖全局变量
- 每条消息/弹窗管理自己的监听器
- 添加安全超时机制，确保监听器一定会被移除
- 添加卡住检测与自动恢复机制

**历史案例**：
- 消息弹窗后界面卡住 → 根本原因：多条消息时后面的消息覆盖了_globalClickInterceptor，导致前面的拦截器无法移除 → 修复：使用局部变量保存每条消息自己的拦截器引用

#### Bug模式3：点击穿透
**现象**：点击弹窗按钮后，下面的按钮也被触发了
**原因**：事件冒泡/延迟点击导致穿透
**易发位置**：弹窗关闭后立即触发底层按钮
**预防方法**：
- 添加点击冷却时间
- 关闭后短时间内阻止点击
- 使用遮罩层拦截
- 全局点击拦截器

#### Bug模式4：状态不同步
**现象**：UI显示和实际状态不一致
**原因**：修改了状态但没有更新UI，或者反之
**易发位置**：属性变化、任务进度、物品数量
**预防方法**：
- 统一状态管理，修改状态后自动触发UI更新
- 每次操作后调用 render() 更新界面
- 添加状态校验机制

#### Bug模式5：数据引用错误
**现象**：显示undefined或者报错"Cannot read property of undefined"
**原因**：引用了不存在的ID
**易发位置**：任务奖励、物品掉落、技能学习
**预防方法**：
- 添加数据存在性检查
- 发布前检查所有引用的ID是否存在
- 写单元测试验证数据一致性

### 8.2 测试技巧

1. **边界测试**：最小值、最大值、0、负数、空值
2. **压力测试**：快速连续点击、大量物品、很长时间
3. **异常路径**：不按正常流程操作、中途取消、返回
4. **兼容性**：不同浏览器、不同分辨率
5. **回归测试**：修复一个bug后，检查相关功能有没有坏

## 九、开发流程规范

### 9.1 开发自测流程

1. 开发完成新功能后
2. 运行 `node --check` 检查所有修改的JS文件语法
3. 本地打开游戏，测试新增功能的基本流程
4. 测试相关联的旧功能是否受影响
5. 检查数据引用是否正确（物品ID/敌人ID/地点ID等）
6. 更新 TODO.md 和 CHANGELOG.md
7. 提交代码，写清楚提交信息

### 9.2 发布前测试流程

1. 完整运行"发布前检查清单"
2. 重点测试消息弹窗系统（最容易出bug的地方）
3. 重点测试新增功能
4. 手机端测试（用户主要用手机玩）
5. 确认所有bug都已修复
6. 推送部署
7. 部署后在线验证

### 9.3 Bug修复流程

1. 复现bug，确认问题
2. 定位根本原因（不要只修表面现象）
3. 修复代码
4. 验证修复有效
5. 检查是否有类似的潜在问题
6. 沉淀经验到文档
7. 提交修复

### 9.4 版本发布流程

**开发阶段**：
- 在master分支直接开发
- 每完成一个小功能就commit
- 提交信息格式：`类型：具体描述`
- 类型包括：Bug修复/功能/优化/文档/结构/测试/内容/平衡

**测试阶段**：
- 本地充分测试
- 按测试用例逐项验证
- 修复发现的所有bug
- 确认没有严重问题

**发布阶段**：
- 更新版本号（player.js / ui.js）
- 更新 CHANGELOG.md
- 更新 TODO.md
- 提交版本更新
- 推送到 GitHub
- 等待 GitHub Pages 自动部署
- 部署后在线验证

**发布后**：
- 监控用户反馈
- 收集bug报告
- 及时修复严重问题
- 总结经验，更新文档
