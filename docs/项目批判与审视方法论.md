# 项目批判与审视方法论

> **核心理念**：本项目是小说《全职法师》改编的网页游戏，单人开发（用户+AI助手）。审视的目的是确保**原著符合、系统健康、体验良好、可扩展**，而非团队协作中的人际问题。

---

## 一、什么时候审视

### 1.1 必须审视的触发点

| 触发点 | 审视范围 | 具体操作 |
|--------|---------|---------|
| **新增小说相关内容后** | 原著符合性 | Grep `全职法师.txt` 验证设定，检查是否超前使用后期设定 |
| **新增系统/机制后** | 系统设计+可扩展性 | 检查是否趋同化、是否需要改核心代码、是否有差异化 |
| **修改战斗/天赋/数值后** | 数据质量+平衡 | 跑 `node tests/run.js` L1+L2，检查数值范围 |
| **修改UI/对话后** | 玩家体验 | 新手视角走一遍流程，检查是否有理解障碍 |
| **每次提交前** | 代码质量 | `node --check` + `node tests/run.js`，检查是否有技术债务 |
| **每个版本发布前** | 全系统 | 按发布检查清单逐项验证 |
| **连续开发3天没停下来时** | 全系统健康度 | 强制停下来，问自己"这样做对吗" |

### 1.2 审视心态切换

> **从"实现者"切换到"批判者"**：写完代码后，假设自己是：
> - 第一次玩这个游戏的玩家——我能理解吗？我会觉得好玩吗？
> - 6个月后要扩展新篇章的开发者——这个设计会成为负担吗？
> - 小说原著党——这个设定符合原著吗？有没有编造？

## 二、五维审视法（本项目定制）

### 2.1 原著符合性审视（本项目最核心）

**为什么重要**：本项目是小说改编，原著符合是底线。编造设定、超前使用后期设定、不符合人物人设都是严重问题。

**检查清单**：
- [ ] **新增NPC/妖魔/技能/物品**：是否Grep了 `全职法师.txt` 验证？是否有原文依据？
- [ ] **NPC修为/系别/天赋**：是否符合小说节奏？是否超前使用了后期设定？（如博城篇就给萧院长加天赋）
- [ ] **重要NPC vs 不重要NPC**：重要NPC必须有明确原文支持，不能随便推断；不重要NPC可合理推断
- [ ] **人设检查**：NPC对话/行为是否符合其人设？（高冷的不主动热情，傲慢的不低声下气）
- [ ] **非原著内容标记**：自己编造的内容是否标记了 `isCanon: false` + `canonNote`？
- [ ] **剧情时间线**：是否符合小说时间线？博城结束后是否还留博城？

**具体操作方法**：
```bash
# 验证某个NPC/设定是否在小说中出现
grep -n "萧院长" 全职法师.txt | head -20

# 验证某个技能/妖魔是否在小说中出现
grep -n "烈拳" 全职法师.txt | head -20

# 检查NPC修为是否符合小说节奏
# 对比小说拆解文档 docs/小说拆解/
```

**常见问题模式**：
- ❌ 重要NPC随便推断天赋/修为（如萧院长博城篇无明确战斗表现却加天赋）
- ❌ 超前使用后期设定（如博城篇就出现高阶魔法的详细设定）
- ❌ 编造小说中不存在的设定且不标记
- ❌ NPC对话不符合人设
- ❌ 剧情时间线混乱（博城结束后还留博城）

### 2.2 系统设计审视（防趋同+保差异化+可扩展）

**为什么重要**：本项目有11系魔法、多个系统（战斗/天赋/剧情/NPC/对话等），趋同化是最大的设计陷阱。每系都搞专属资源、每个系统都用同样的模板，会让游戏变得无聊。

**检查清单**：
- [ ] **趋同化检测**：是否出现"每个X都有一个Y"的模式？（如每系都搞专属资源机制）
- [ ] **差异化设计**：不同系别/系统是否有独特的机制和体验？（如火系燃点积累、冰系控制、雷系高爆发）
- [ ] **可扩展性检测**：新增系别/妖魔/NPC时，是否需要修改核心代码？还是只加数据？
- [ ] **复杂度合理性**：引入的复杂度是否带来了足够的价值？还是为了复杂而复杂？
- [ ] **方案评估**：是否考虑了至少2种备选方案？当前方案是否最优？
- [ ] **与玩家机制对齐**：NPC法师/敌人法师的战斗机制是否与玩家对齐？（如系别等级加成、天赋、技能）

**趋同化检测具体方法**：
1. 列出所有系别的核心机制
2. 检查是否有"每个系都用了同样的模式"
3. 问自己：如果去掉这个通用模式，每个系是否还能独立成立？
4. 如果答案是"不能"，说明趋同化严重，需要重新设计差异化

**可扩展性检测具体方法**：
1. 想象要新增第12系魔法（如音系），需要改多少个文件？
2. 理想情况：只加数据（skills.js/talents.js等），不需要改核心代码
3. 如果需要改battle.js/game.js等核心代码，说明可扩展性有问题

**常见问题模式**：
- ❌ 每系都搞专属资源机制（趋同化）
- ❌ 所有天赋都是"伤害加成+暴击加成"的模板（趋同化）
- ❌ 新增系别需要改核心代码（可扩展性差）
- ❌ NPC法师战斗机制与玩家不对齐（如系别等级加成仅玩家生效）
- ❌ 为了复杂而复杂，引入不必要的机制

### 2.3 数据质量审视（完整+合理+无冗余）

**为什么重要**：本项目是数据驱动，数据质量直接影响游戏体验。悬空引用、数值失衡、冗余数据都会导致bug和体验问题。

**检查清单**：
- [ ] **数据完整性**：引用的ID是否都存在？是否有悬空引用？（运行L1测试）
- [ ] **ID不重复**：新增数据的ID是否与已有重复？（Grep确认）
- [ ] **数值合理性**：伤害/HP/MP/概率是否在合理范围内？是否有明显失衡？
- [ ] **格式一致性**：字段命名/格式是否统一？是否有混用？（如element vs elements）
- [ ] **冗余检测**：是否有重复数据？是否有从未使用的数据？
- [ ] **interruptChance覆盖**：施法类型的中阶/高阶魔法是否都设置了interruptChance？

**具体操作方法**：
```bash
# 运行L1数据完整性测试
node tests/run.js

# 检查ID不重复
grep -n "id: \"new_skill\"" engine/data/skills.js

# 统计各系技能数量，检查是否均衡
node -e "const skills = require('./engine/data/skills.js'); ..."

# 检查中阶魔法的interruptChance覆盖
node -e "const skills = require('./engine/data/skills.js'); 检查tier==='中阶'且type==='damage'的技能是否有interruptChance"
```

**常见问题模式**：
- ❌ 悬空引用（引用了不存在的技能/物品/妖魔ID）
- ❌ ID重复（新增数据与已有数据ID冲突）
- ❌ 数值失衡（某个技能伤害过高/过低）
- ❌ 格式不一致（有的用element，有的用elements）
- ❌ 施法类型魔法遗漏interruptChance（如地波/暗影之刺）
- ❌ 冗余数据（重复的技能/物品，或从未使用的数据）

### 2.4 玩家体验审视（可理解+有反馈+无压力+有代入感）

**为什么重要**：玩家体验感最重要。功能正常≠好玩，体验问题和bug同等重要。

**检查清单**：
- [ ] **可理解性**：玩家能理解这个机制吗？是否需要过多的说明？（如"探索0/1"是什么意思）
- [ ] **选择压力**：是否给玩家造成了不必要的选择焦虑？（如修炼四档时间选择）
- [ ] **反馈及时性**：玩家操作后是否有即时反馈？（如接任务后是否弹窗，而不是关掉对话才弹）
- [ ] **节奏合理性**：是否有过长的等待？是否有过于密集的操作？（如日常事情做完后是否还有时间探索）
- [ ] **自由度**：玩家是否有足够的选择空间？是否被线性剧情束缚？
- [ ] **代入感**：是否破坏了玩家的沉浸感？（如突兀的UI、不符合人设的对话、下拉选择框做主副修选择）
- [ ] **信息密度**：一屏内的信息量是否过载？关键信息是否突出？（如效果名称显示代码命名而非中文）

**具体测试方法**：
1. **新手视角测试**：假设自己是第一次玩的玩家，从新建角色开始走一遍，记录所有"这是什么意思"的时刻
2. **极端情况测试**：如果玩家一直不做某件事会怎样？如果玩家做了意料之外的选择会怎样？
3. **情感曲线测试**：玩家在这个过程中的情绪是怎样的？是否有低谷？
4. **信息密度测试**：一屏内的信息量是否过载？关键信息是否突出？

**常见问题模式**：
- ❌ 不必要的选择压力（如修炼四档时间选择，玩家不知道选哪个好）
- ❌ 反馈不及时（如接任务后不弹窗，关掉对话才弹）
- ❌ 信息不可理解（如"探索0/1"、效果名称显示代码命名）
- ❌ UI突兀（如下拉选择框做主副修选择、全屏弹窗遮挡战斗场地）
- ❌ 节奏不合理（如日常事情做完后没有时间探索）
- ❌ 代入感破坏（如不符合人设的对话、玩家被线性剧情束缚）

### 2.5 代码质量审视（可维护+无债务+无bug模式）

**为什么重要**：本项目会持续扩展（博城篇→后续篇章），代码质量直接影响扩展效率。技术债务会越积越多，最终导致无法扩展。

**检查清单**：
- [ ] **语法正确**：`node --check` 所有修改的JS文件
- [ ] **测试通过**：`node tests/run.js` 0失败
- [ ] **职责分离**：数据层/逻辑层/UI层是否清晰分离？（如battle.js是否既做逻辑又做UI）
- [ ] **技术债务**：是否有临时方案？是否有TODO/FIXME标记？是否有"先这样以后再改"的代码？
- [ ] **重复代码**：是否有复制粘贴的代码块？应该抽象为函数？
- [ ] **魔法数字**：是否有硬编码的100/0.5等没有注释说明的数字？
- [ ] **bug模式**：是否符合已知的bug模式？（参考 `docs/开发踩坑记录与通用经验.md`）

**具体操作方法**：
```bash
# 语法检查
node --check engine/battle.js

# 运行测试
node tests/run.js

# 检查是否有TODO/FIXME
grep -rn "TODO\|FIXME\|HACK\|XXX" engine/

# 检查重复代码（手动审查，或使用工具）
# 检查文件行数，超过500行的文件可能需要拆分
wc -l engine/*.js
```

**已知bug模式（参考踩坑记录）**：
- ❌ 批量脚本插入字段时，Windows换行符(\r)导致语法错误
- ❌ 批量替换对象key时，全局正则第一个匹配可能是relationship中的引用而非对象key
- ❌ npc.growth只有base没有events时，for...of迭代报TypeError
- ❌ node -e中含中文引号导致SyntaxError
- ❌ Edit工具OLD_STRING不唯一时失败

## 三、审视流程（四步法）

### 第一步：收集事实

- 读取相关代码和数据
- 运行自动化测试（`node tests/run.js`）
- Grep小说原文验证设定（`grep -n "关键词" 全职法师.txt`）
- 记录用户反馈和已知问题

**不要在事实不清时下结论。**

### 第二步：识别问题

- 对照五维审查清单逐项检查
- 标记发现的问题，按严重程度分级（P0阻塞/P1重要/P2一般/P3建议）
- 区分"事实问题"（确定是bug）和"设计选择"（可以讨论的方案）

### 第三步：评估影响

- 这个问题影响多少玩家？
- 修复成本有多高？
- 不修复会有什么后果？
- 是否有临时规避方案？
- 是否符合"小说驱动，数据驱动"原则？

### 第四步：决策行动

| 严重程度 | 行动 |
|---------|------|
| P0阻塞 | 立即修复，阻塞发布 |
| P1重要 | 本版本修复，或记录到下版本TODO |
| P2一般 | 记录到TODO，按优先级排期 |
| P3建议 | 记录到"待讨论"，积累后统一评估 |

## 四、审视工具与模板

### 4.1 每次提交前快速检查清单

```
[ ] node --check 所有修改的JS文件
[ ] node tests/run.js 0失败
[ ] 新增数据ID不重复（Grep确认）
[ ] 引用的技能/物品/妖魔已存在
[ ] 涉及小说内容已回原文验证（Grep全职法师.txt）
[ ] 人设检查通过（NPC互动符合人设）
[ ] TODO.md已更新
[ ] 提交信息清晰描述改动内容
[ ] 本次改动是否引入了技术债务？如有，是否记录？
```

### 4.2 新系统/大功能完成后审查清单

```
[ ] 设计文档是否完整？
[ ] 是否考虑了至少2种备选方案？
[ ] 是否与用户对齐确认？
[ ] 原著符合性检查（如涉及小说内容）
[ ] 趋同化检测（是否每系都用了同样的模式？）
[ ] 差异化设计评估（不同系别/系统是否有独特机制？）
[ ] 可扩展性评估（新增系别/妖魔/NPC是否需要改核心代码？）
[ ] 数值平衡初步验证
[ ] 测试用例是否覆盖？
[ ] 文档是否同步？
```

### 4.3 版本发布前全面检查清单

```
[ ] 全系统自动化测试通过（node tests/run.js）
[ ] 冒烟测试通过（能进游戏/能修炼/能对话/能战斗）
[ ] 黑盒测试报告已完成
[ ] 已知P0/P1问题已修复或有规避方案
[ ] 数据一致性检查通过
[ ] 原著符合性抽查（随机抽取10个NPC/技能/妖魔验证）
[ ] 文档同步完成（TODO/CHANGELOG/README/AGENTS）
[ ] 版本号已更新
[ ] Git提交历史清晰
[ ] 回滚方案已准备
```

### 4.4 问题记录模板

```markdown
### 问题标题
- **严重程度**：P0/P1/P2/P3
- **维度**：原著符合/系统设计/数据质量/玩家体验/代码质量
- **现象描述**：具体是什么问题
- **复现步骤**：如何复现（如适用）
- **根因分析**：为什么会出现这个问题
- **影响范围**：影响哪些系统/玩家
- **建议方案**：如何修复
- **修复成本**：预估工作量
- **状态**：待评估/已确认/修复中/已修复/已放弃
```

## 五、本项目特有的审视原则

### 5.1 原著优先原则

> 涉及小说内容时，原著符合是底线。宁可少加内容，也不要编造设定。

- 重要NPC必须有明确原文支持，不能随便推断
- 不重要NPC可合理推断，但要标记推断依据
- 超前使用后期设定是严重问题
- 非原著内容必须标记 `isCanon: false`

### 5.2 玩家体验优先原则

> 功能正常≠好玩，体验问题和bug同等重要。

- 不必要的选择压力要消除（如修炼四档时间选择）
- 反馈要及时（如接任务后立即弹窗）
- 信息要可理解（不要显示代码命名，要用中文完整解释）
- UI要自然（不要用下拉选择框做主副修选择，不要用全屏弹窗遮挡战斗场地）

### 5.3 差异化防趋同原则

> 每系魔法、每个系统都应该有独特的机制和体验，不能用模板套。

- 不要每系都搞专属资源机制
- 不要所有天赋都是"伤害加成+暴击加成"的模板
- 不同系别应该有不同的核心玩法（如火系燃点积累、冰系控制、雷系高爆发）
- 参考其他游戏（崩坏星穹铁道、宝可梦）的差异化设计

### 5.4 数据驱动可扩展原则

> 能用数据配置的不改代码，新增内容应该只加数据不改核心。

- 新增系别/妖魔/NPC应该只加数据文件，不需要改battle.js/game.js等核心代码
- 如果需要改核心代码，说明可扩展性有问题，需要重新设计
- 数据格式要统一，不要混用（如element vs elements）

### 5.5 技术债务可控原则

> 技术债务不可避免，但要可控、可追踪、可偿还。

- 临时方案要标记TODO/FIXME
- 不要有"先这样以后再改"但不记录的代码
- 每个版本至少偿还一部分技术债务
- 已知bug模式要记录到踩坑文档，避免重复踩坑

## 六、持续改进闭环

```
审视 → 发现问题 → 记录 → 优先级排序 → 修复 → 验证 → 沉淀经验 → 再审视
```

**关键**：审视不是一次性活动，而是持续的习惯。每次审视都要比上一次更深入、更高效。

**经验沉淀去向**：
- 新发现的bug模式 → `docs/开发踩坑记录与通用经验.md`
- 新的设计方法论 → 本文档或对应系统设计文档
- 新的测试方法 → `docs/测试方法论.md`
- 新的开发流程改进 → AGENTS.md
- 新的原著校准发现 → `docs/博城篇原文回归校准报告.md`
