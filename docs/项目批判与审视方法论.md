# 项目批判与审视方法论

> **核心理念**：批判不是否定，而是持续改进的驱动力。通过结构化的审视，发现设计缺陷、技术债务和体验问题，确保项目长期健康发展。

---

## 一、什么时候反思和审视

### 1.1 触发时机（必须审视）

| 时机 | 审视范围 | 深度 |
|------|---------|------|
| **每个版本发布前** | 全系统：代码/设计/数据/体验 | 全面深度审视 |
| **每个大功能/系统完成后** | 该系统及其影响范围 | 专项深度审视 |
| **遇到设计冲突或用户反馈问题时** | 相关系统及根因 | 根因分析+方案评估 |
| **每次提交前** | 本次改动的代码和数据 | 快速代码审查 |
| **定期（每2周）** | 全项目健康度 | 中等深度巡检 |

### 1.2 自主触发（建议审视）

- 连续开发超过3天没有停下来思考时
- 感觉"这样做可能不太对"但说不出原因时
- 新增代码量超过200行时
- 修改了核心系统（战斗/天赋/剧情）时
- 用户连续反馈同类问题时

### 1.3 审视心态

> **从"作者"切换到"批判者"**：写完代码后，假设自己是第一次看到这段代码的陌生人，问自己：
> - 我能理解这段代码在做什么吗？
> - 如果我要修改它，会害怕吗？
> - 有没有更简单的方式实现同样的功能？
> - 这个设计会给未来的扩展带来麻烦吗？

## 二、如何审视（五维审视法）

### 2.1 代码维度

**审查清单**：
- [ ] **可读性**：变量名/函数名是否清晰？逻辑是否易懂？是否有不必要的奇淫巧技？
- [ ] **简洁性**：是否有重复代码？是否符合KISS（保持简单）和DRY（不要重复）原则？
- [ ] **可维护性**：分层是否清晰？模块化是否合理？是否高内聚低耦合？
- [ ] **可扩展性**：是否仅仅满足一次性需求？是否有必要的前瞻性扩展设计？
- [ ] **可测试性**：是否容易编写单元测试？是否有副作用难以隔离？
- [ ] **错误处理**：边界情况是否处理？空值/异常是否有防御？

**常见问题模式**：
- 一个函数做了太多事情（超过50行或3个职责）
- 全局状态泛滥，难以追踪数据流向
- 魔法数字（硬编码的100/0.5等）没有注释说明
- 复制粘贴的代码块，应该抽象为函数
- 注释与代码不一致（注释过时）

### 2.2 设计维度

**审查清单**：
- [ ] **核心原则符合性**：是否符合AGENTS.md的9大核心原则？
- [ ] **趋同化检测**：是否每个系统都用了同样的模式？（如每系都搞专属资源）
- [ ] **差异化设计**：不同系别/系统是否有独特的机制和体验？
- [ ] **方案评估**：是否考虑了至少2种备选方案？当前方案是否最优？
- [ ] **复杂度合理性**：引入的复杂度是否带来了足够的价值？
- [ ] **与原著一致性**：是否符合小说原文设定？是否超前使用了后期设定？

**趋同化检测方法**：
1. 列出所有系别/系统的核心机制
2. 检查是否有"每个X都有一个Y"的模式
3. 问自己：如果去掉这个通用模式，每个系统是否还能独立成立？
4. 如果答案是"不能"，说明趋同化严重，需要重新设计差异化

**设计反思三问**：
1. **这个设计解决了什么问题？**（如果答不上来，可能是过度设计）
2. **有没有更简单的方式？**（简单方案优先，复杂方案需要充分理由）
3. **未来会后悔吗？**（想象6个月后回头看，这个设计会成为负担吗？）

### 2.3 数据维度

**审查清单**：
- [ ] **原著一致性**：NPC修为/技能/妖魔强度是否符合小说原文？
- [ ] **数值合理性**：伤害/HP/MP/概率是否在合理范围内？是否有明显失衡？
- [ ] **数据完整性**：引用的ID是否都存在？是否有悬空引用？
- [ ] **冗余检测**：是否有重复数据？是否有从未使用的数据？
- [ ] **格式一致性**：字段命名/格式是否统一？是否有混用？
- [ ] **可追溯性**：非原著内容是否标记了isCanon和canonNote？

**数据一致性检查工具**：
- `node tests/run.js` L1数据完整性测试
- Grep搜索确认ID不重复
- 对比小说原文验证设定

### 2.4 体验维度

**审查清单**：
- [ ] **可理解性**：玩家能理解这个机制吗？是否需要过多的说明？
- [ ] **选择压力**：是否给玩家造成了不必要的选择焦虑？（如四档时间选择）
- [ ] **反馈及时性**：玩家操作后是否有即时反馈？（如接任务后是否弹窗）
- [ ] **节奏合理性**：是否有过长的等待？是否有过于密集的操作？
- [ ] **自由度**：玩家是否有足够的选择空间？是否被线性剧情束缚？
- [ ] **代入感**：是否破坏了玩家的沉浸感？（如突兀的UI/不符合人设的对话）

**体验测试方法**：
1. **新手视角测试**：假设自己是第一次玩的玩家，能否自然理解？
2. **极端情况测试**：如果玩家一直不做某件事会怎样？如果玩家做了意料之外的选择会怎样？
3. **情感曲线测试**：玩家在这个过程中的情绪是怎样的？是否有低谷？
4. **信息密度测试**：一屏内的信息量是否过载？关键信息是否突出？

### 2.5 架构维度

**审查清单**：
- [ ] **职责分离**：数据层/逻辑层/UI层是否清晰分离？
- [ ] **依赖方向**：是否有循环依赖？是否有高层依赖低层的反向依赖？
- [ ] **技术债务**：是否有临时方案？是否有TODO/FIXME标记？
- [ ] **可扩展性**：新增系别/妖魔/NPC时，是否需要修改核心代码？
- [ ] **性能隐患**：是否有O(n²)的循环？是否有频繁的DOM操作？
- [ ] **状态管理**：全局状态是否可控？是否有难以追踪的状态变更？

**架构健康度信号**：
- 新增一个系别需要修改多少个文件？（越少越好，理想情况只加数据）
- 修复一个bug是否会引发另一个bug？（如果是，说明耦合严重）
- 是否有"上帝对象"（一个文件/类做了所有事情）？
- 是否有"霰弹枪修改"（一个简单改动需要修改很多地方）？

## 三、审视流程（四步法）

### 第一步：收集事实

- 读取相关代码和数据
- 运行自动化测试
- 检索小说原文验证设定
- 记录用户反馈和已知问题

**不要在事实不清时下结论。**

### 第二步：识别问题

- 对照五维审查清单逐项检查
- 标记发现的问题，按严重程度分级（P0阻塞/P1重要/P2一般/P3建议）
- 区分"事实问题"（确定是bug）和"观点问题"（可以讨论的设计选择）

### 第三步：评估影响

- 这个问题影响多少玩家？
- 修复成本有多高？
- 不修复会有什么后果？
- 是否有临时规避方案？

### 第四步：决策行动

| 严重程度 | 行动 |
|---------|------|
| P0阻塞 | 立即修复，阻塞发布 |
| P1重要 | 本版本修复，或记录到下版本TODO |
| P2一般 | 记录到TODO，按优先级排期 |
| P3建议 | 记录到"待讨论"，积累后统一评估 |

## 四、审视工具与模板

### 4.1 代码审查清单（每次提交前）

```
[ ] node --check 所有修改的JS文件
[ ] node tests/run.js 0失败
[ ] 新增数据ID不重复
[ ] 引用的技能/物品/妖魔已存在
[ ] 涉及小说内容已回原文验证
[ ] 人设检查通过（NPC互动符合人设）
[ ] TODO.md已更新
[ ] 提交信息清晰描述改动内容
[ ] 本次改动是否引入了技术债务？如有，是否记录？
```

### 4.2 系统设计审查清单（新系统完成后）

```
[ ] 设计文档是否完整？
[ ] 是否考虑了至少2种备选方案？
[ ] 是否与用户对齐确认？
[ ] 核心原则符合性检查
[ ] 趋同化检测
[ ] 差异化设计评估
[ ] 可扩展性评估
[ ] 数值平衡初步验证
[ ] 测试用例是否覆盖？
[ ] 文档是否同步？
```

### 4.3 版本发布前全面审视清单

```
[ ] 全系统自动化测试通过
[ ] 冒烟测试通过（能进游戏/能修炼/能对话/能战斗）
[ ] 黑盒测试报告已完成
[ ] 已知P0/P1问题已修复或有规避方案
[ ] 数据一致性检查通过
[ ] 文档同步完成（TODO/CHANGELOG/README/AGENTS）
[ ] 版本号已更新
[ ] Git提交历史清晰
[ ] 回滚方案已准备
```

### 4.4 问题记录模板

```markdown
### 问题标题
- **严重程度**：P0/P1/P2/P3
- **维度**：代码/设计/数据/体验/架构
- **现象描述**：具体是什么问题
- **复现步骤**：如何复现（如适用）
- **根因分析**：为什么会出现这个问题
- **影响范围**：影响哪些系统/玩家
- **建议方案**：如何修复
- **修复成本**：预估工作量
- **状态**：待评估/已确认/修复中/已修复/已放弃
```

## 五、批判的原则与禁忌

### 5.1 批判原则

1. **对事不对人**：批判的是代码和设计，不是开发者
2. **基于事实**：用数据和代码说话，不用"我觉得"
3. **建设性**：指出问题的同时给出改进建议
4. **优先级**：先解决阻塞问题，再讨论优化建议
5. **可操作**：每个问题都应该有明确的行动项
6. **记录沉淀**：发现的问题和解决方案要记录到文档，避免重复踩坑

### 5.2 批判禁忌

1. **❌ 完美主义陷阱**：不要追求100分，80分能发布就发布，剩余20分持续迭代
2. **❌ 过度设计**：不要为了"可能的未来需求"引入不必要的复杂度
3. **❌ 分析瘫痪**：不要一直分析不行动，设定时间盒，到点就决策
4. **❌ 否定一切**：批判不是否定，好的设计要肯定，问题要改进
5. **❌ 事后诸葛亮**：不要用现在的认知批判过去的决策，要考虑当时的上下文
6. **❌ 只破不立**：只指出问题不给方案，是无效的批判

## 六、持续改进闭环

```
审视 → 发现问题 → 记录 → 优先级排序 → 修复 → 验证 → 沉淀经验 → 再审视
```

**关键**：审视不是一次性活动，而是持续的习惯。每次审视都要比上一次更深入、更高效。

**经验沉淀**：
- 新发现的bug模式 → `docs/开发踩坑记录与通用经验.md`
- 新的设计方法论 → 本文档或对应系统设计文档
- 新的测试方法 → `docs/测试方法论.md`
- 新的开发流程改进 → AGENTS.md 或 Skill references
