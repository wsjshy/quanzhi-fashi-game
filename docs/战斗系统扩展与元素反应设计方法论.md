# 战斗系统扩展与元素反应设计方法论

> 沉淀自 v3.6.0 元素反应系统深化开发 | 日期：2026-09-07

## 一、战斗系统扩展方法论

### 1.1 扩展前的现状分析

在添加新战斗机制前，必须先回答三个问题：
1. **现有实现到什么程度？** —— 不要从零开始，先找已有框架
2. **痛点是什么？** —— 是功能缺失、数值不平衡、还是体验问题？
3. **改动范围有多大？** —— 是改一个函数，还是需要架构调整？

**v3.6.0实例**：
- 已有4种元素反应（感电/融化/蒸汽/泥泞），但只改变状态，无伤害
- 痛点：玩家感知不到元素反应的价值，策略深度不足
- 改动：需要添加伤害计算、扩充反应类型、优化架构

### 1.2 渐进式扩展策略

| 步骤 | 动作 | 目的 |
|------|------|------|
| 1 | 保留原调用接口 | 不破坏现有代码 |
| 2 | 内部替换实现 | 用新模块替换旧逻辑 |
| 3 | 模拟状态测试 | 不依赖真实战斗流程，快速验证 |
| 4 | 真实战斗验证 | 确保端到端正常 |

**关键原则**：**接口不变，内部升级**。`checkElementReactions(target, effect, isPlayerTarget)` 的签名完全不变，只是内部从50行硬编码改为调用独立模块。

### 1.3 模拟状态测试法

战斗系统测试的难点是需要完整的战斗流程。解决方案：**用JS模拟战斗状态，直接调用目标函数**。

```javascript
// 模拟战斗状态
BattleSystem.player = { hp: 200, attack: 60, statusEffects: [] };
BattleSystem.enemy = { name: '测试', hp: 150, attack: 40, statusEffects: [] };
BattleSystem.addLog = function(msg) { this._lastLog = msg; };
BattleSystem.showDamageNumber = function() {};

// 直接测试元素反应
BattleSystem.enemy.statusEffects = [{ type: 'wet', name: '湿润' }];
BattleSystem.checkElementReactions(BattleSystem.enemy, { element: 'thunder' }, false);
```

**优势**：
- 0.1秒完成测试，不需要进入战斗
- 可以精确控制初始状态
- 可以验证边界情况（多反应同时触发、空状态等）

## 二、元素反应系统设计方法论

### 2.1 反应表三要素

每个元素反应必须明确定义三个要素：

| 要素 | 说明 | 示例 |
|------|------|------|
| **trigger** | 触发条件（什么元素+什么状态） | 雷元素 + 湿润状态 |
| **apply** | 效果（状态变化） | 湿润→感电，持续伤害 |
| **damageMultiplier** | 伤害倍率 | 1.0x攻击力 |

**数据驱动设计**：将反应配置为数据表，而非硬编码if-else：

```javascript
const REACTIONS = {
    electrified: {
        name: '感电',
        icon: '⚡',
        damageMultiplier: 1.0,
        trigger: (effect, targetEffects) => { /* 判断逻辑 */ },
        apply: (target, effect) => { /* 效果逻辑 */ }
    }
};
```

**优势**：新增反应只需添加配置项，不需要修改核心逻辑。

### 2.2 优先级系统

当多个反应可同时触发时（如火+冰+水同时存在），必须有明确的优先级规则：

**设计原则**：按伤害倍率从高到低排序，高优先级反应先触发，触发后消耗元素状态。

```javascript
const PRIORITY = Object.entries(REACTIONS)
    .sort((a, b) => b[1].damageMultiplier - a[1].damageMultiplier)
    .map(([key]) => key);
```

**为什么需要优先级**：
- 避免一回合触发多个反应导致数值爆炸
- 让玩家有明确的预期（知道哪个反应会触发）
- 符合"高风险高回报"设计（难触发的反应伤害更高）

### 2.3 伤害计算原则

元素反应伤害的设计原则：

1. **基于施法者属性**：攻击力 × 倍率，让攻击属性有价值
2. **无视防御**：确保低攻击玩家也能通过反应打出可观伤害
3. **不享受暴击**：反应伤害是固定收益，不是随机收益
4. **每回合最多1次**：避免连续触发导致不平衡

**设计哲学**：元素反应是"策略奖励"，不是"数值碾压"。玩家通过合理的技能顺序触发反应，获得额外收益，但不应该让反应成为唯一的输出来源。

## 三、架构优化方法论：从大文件提取独立模块

### 3.1 识别提取时机

当满足以下条件时，应该考虑提取独立模块：
- 功能内聚（元素反应的所有逻辑都在一起）
- 代码量超过50行
- 未来可能扩展（新增反应类型）
- 与核心逻辑耦合度低（只需要target/effect/caster三个参数）

### 3.2 提取步骤

| 步骤 | 动作 | 验证 |
|------|------|------|
| 1 | 创建新模块文件，导出纯函数 | 语法检查 |
| 2 | 将原逻辑迁移到新模块 | 单元测试 |
| 3 | 原文件保留薄包装方法 | 调用接口不变 |
| 4 | 删除原文件中的冗余代码 | 自动化测试通过 |
| 5 | 浏览器端到端验证 | 真实场景正常 |

### 3.3 薄包装模式

原文件不直接删除方法，而是保留一个薄包装：

```javascript
// battle.js 中保留
checkElementReactions(target, newEffect, isPlayerTarget) {
    const caster = isPlayerTarget ? this.enemy : this.player;
    checkElementReactionsImpl(this, target, newEffect, isPlayerTarget, caster);
}
```

**为什么保留薄包装**：
- 所有调用处不需要修改（`this.checkElementReactions()` 仍然有效）
- 可以在这里处理战斗实例特有的逻辑（如推断施法者）
- 向后兼容，降低风险

## 四、可玩性评审清单

在设计战斗新机制时，用以下清单评审可玩性：

- [ ] **策略深度**：玩家是否需要做选择？（如技能顺序、元素搭配）
- [ ] **可感知性**：玩家是否能看到/感受到机制的存在？（伤害数字、日志、UI提示）
- [ ] **低门槛**：新手是否能无意触发并获得收益？
- [ ] **高上限**：高手是否能通过精细操作获得更高收益？
- [ ] **原著契合**：是否符合小说设定？
- [ ] **数值平衡**：是否会让某套阵容过于强势？
- [ ] **扩展性**：未来添加新元素/新反应是否方便？

**v3.6.0评审结果**：
- 策略深度：✅ 多系法师有更多反应组合，技能顺序很重要
- 可感知性：✅ 伤害数字+高亮日志，玩家能明确看到反应触发
- 低门槛：✅ 无意触发也能获得额外伤害
- 高上限：✅ 高手可以通过"上水→上雷"的顺序稳定触发感电
- 原著契合：✅ 雷在水中威力大增等符合原著
- 数值平衡：⚠️ 需后续观察，爆裂2.0x倍率可能偏高
- 扩展性：✅ 配置表驱动，新增反应只需加配置项

## 五、后续优化方向

1. **元素附着UI**：在战斗界面显示目标当前附着的元素状态图标
2. **元素精通天赋**：增加"元素反应伤害+X%"的天赋
3. **扩散反应**：风系技能扩散元素到全体敌人（需处理多目标逻辑）
4. **反应连锁**：一个反应触发后为下一个反应创造条件（如融化解除冻结后可接感电）
5. **数值平衡**：根据实际战斗数据调整各反应倍率
