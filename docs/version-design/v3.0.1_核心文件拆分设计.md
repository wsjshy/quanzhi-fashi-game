# v3.0.1 核心文件拆分设计

> 阶段二：将battle.js(8875行)、ui.js(7702行)、game.js(5657行)拆分为更小的功能模块
> 原则：渐进式拆分，每次拆分一个模块，拆分后立即运行测试，保持向后兼容

## 一、拆分策略

### 1.1 核心原则
- **渐进式**：每次只拆分一个功能模块，不一次性重写
- **向后兼容**：原文件保留，re-export拆分后的模块，确保现有引用不失效
- **测试驱动**：拆分后立即运行L1-L3测试，确保功能不破坏
- **单一职责**：每个模块只负责一个明确的功能领域

### 1.2 拆分方法
1. 识别独立的功能模块（方法聚合、数据内聚）
2. 创建新文件，将相关方法和数据迁移过去
3. 原文件中删除已迁移的代码，改为import新模块
4. 运行测试验证
5. 提交代码

## 二、battle.js 拆分方案

### 当前状态
- 总行数：8875行
- 主要方法：75个
- 已独立模块：battle-ai.js、battle-effect.js、battle-event.js

### 拆分计划

#### 模块1：battle-ui.js（战斗UI渲染）
- **职责**：战斗界面的HTML渲染、技能面板、角色展示、伤害数字
- **预估行数**：~2500行
- **包含方法**：renderBattleScreen、renderSkillPanel、showDamageNumber、renderBattleLog等
- **依赖**：BattleSystem（状态）、UI（通用UI工具）

#### 模块2：battle-calculator.js（战斗数值计算）
- **职责**：伤害计算、元素克制、暴击、防御、状态效果数值
- **预估行数**：~1500行
- **包含方法**：calculateDamage、calculateElementMultiplier、calculateCrit、applyStatusEffect等
- **依赖**：纯函数，无外部依赖

#### 模块3：battle-action.js（战斗行动处理）
- **职责**：玩家/敌人行动处理、技能释放、物品使用、逃跑
- **预估行数**：~2000行
- **包含方法**：playerAttack、playerCastSkill、playerDefend、playerUseItem、playerFlee、enemyTurn等
- **依赖**：battle-calculator、battle-ui、BattleSystem状态

#### 模块4：battle-system.js（战斗主流程）
- **职责**：战斗初始化、回合管理、胜负判定、状态管理
- **预估行数**：~1500行
- **包含方法**：startBattle、nextTurn、checkBattleEnd、initBattleState等
- **依赖**：battle-action、battle-ui、battle-ai

### 拆分顺序
1. battle-calculator.js（纯函数，最独立，风险最低）
2. battle-ui.js（UI渲染，与逻辑解耦）
3. battle-action.js（行动处理）
4. battle-system.js（主流程，最后整合）

## 五、风险与应对

### 5.1 风险
1. **循环依赖**：拆分后模块间可能出现循环依赖
   - 应对：使用事件总线/回调解耦，或合并相关模块
2. **全局变量引用**：现有代码大量使用全局变量，拆分后可能失效
   - 应对：保持window挂载兼容，逐步改为import
3. **测试覆盖不足**：部分功能没有自动化测试，拆分后可能引入bug
   - 应对：拆分后进行冒烟测试+手动验证关键流程
4. **HTML onclick引用**：HTML中直接调用全局函数，拆分后函数可能不在window上
   - 应对：保持关键函数的window挂载，逐步改为事件委托

### 5.2 回滚策略
- 每次拆分一个模块后提交代码，出现问题可回退到上一个commit
- 原文件保留re-export，确保向后兼容

## 六、验收标准

1. 每个拆分后的模块行数不超过2000行
2. L1-L3自动化测试全部通过（128+测试用例）
3. 游戏关键流程正常（启动→角色创建→主界面→战斗→对话→存档）
4. 无循环依赖
5. 代码可维护性提升（模块职责清晰，易于定位问题）
