# v3.0.2 状态管理与存档升级设计

> 版本：v3.0.2 | 状态：设计中 | 最后更新：2026-08-22

## 一、背景与问题

### 当前存档系统现状
- `Player.save()` 手动序列化 **60+ 字段**（name/level/exp/elements/talents/...）
- `Player.load()` 手动加载每个字段，大量 `?? 默认值` 处理
- 子系统（Inventory/WorldState/NPCStateSystem）通过各自的 `getSaveData()` / `loadSaveData()` 单独处理
- 存档迁移 `_migrateSave()` 是线性if链，每次版本升级都要手动添加迁移逻辑

### 核心问题
1. **新增字段易漏存**：每次给Player加新属性，必须同时改save()和load()，漏一个就数据丢失
2. **迁移逻辑脆弱**：线性if链，版本跳跃时容易漏迁移步骤
3. **状态分散**：玩家状态在Player，世界状态在WorldState，NPC状态在NPCStateSystem，没有统一视图
4. **无schema校验**：存档损坏或字段缺失时只能靠默认值兜底，无法检测异常

## 二、设计目标

1. **集中式状态管理**：建立 `GameState` 容器，统一管理所有可序列化状态
2. **声明式schema**：字段在schema中声明一次，自动参与save/load/默认值/迁移
3. **版本化迁移链**：存档带version，加载时按版本号链式执行迁移函数
4. **向后兼容**：旧存档（v0.1.0~v3.0.1）必须能正常加载和迁移
5. **不改变功能**：纯架构重构，游戏逻辑和体验不变

## 三、方案设计

### 3.1 GameState 状态容器

```
src/engine/game-state.js
├── stateSchema: 字段声明（key, default, migrate）
├── state: 运行时状态对象（代理）
├── save(): 序列化到localStorage
├── load(): 从localStorage加载+迁移
├── migrate(data, fromVersion): 版本迁移链
└── get/set: 状态访问（兼容Player.xxx直接访问）
```

### 3.2 字段声明schema

```js
const STATE_SCHEMA = {
  // 玩家基础
  name: { default: '冒险者', category: 'player' },
  level: { default: 1, category: 'player' },
  exp: { default: 0, category: 'player' },
  // ... 60+字段
  
  // 子系统状态
  inventory: { default: {}, category: 'subsystem', serialize: () => Inventory.getSaveData() },
  worldState: { default: null, category: 'subsystem', serialize: () => WorldState.getSaveData() },
  npcStates: { default: null, category: 'subsystem', serialize: () => NPCStateSystem.getSaveData() },
  
  // 元数据
  saveVersion: { default: '3.0.2', category: 'meta' },
  saveTime: { default: null, category: 'meta' },
};
```

### 3.3 版本迁移链

```js
const MIGRATIONS = [
  { from: '0.1.0', to: '0.2.0', fn: (data) => {...} },
  { from: '0.2.0', to: '0.3.0', fn: (data) => {...} },
  // ... 历史迁移
  { from: '3.0.1', to: '3.0.2', fn: (data) => { /* 新格式，基本无需改动 */ } },
];

function migrate(data) {
  let version = data.saveVersion || '0.1.0';
  for (const m of MIGRATIONS) {
    if (compareVersion(version, m.from) < 0) {
      data = m.fn(data);
      version = m.to;
    }
  }
  data.saveVersion = CURRENT_VERSION;
  return data;
}
```

### 3.4 向后兼容策略

**关键原则：渐进式迁移，不一次性重写**

1. **第一阶段**：建立GameState容器，但Player.save()/load()内部委托给GameState
2. **第二阶段**：Player的字段通过 `Object.defineProperty` 代理到GameState.state，保持 `Player.level` 直接访问不变
3. **第三阶段**：子系统（Inventory/WorldState/NPCStateSystem）注册到GameState，统一序列化

**这样所有调用 `Player.xxx` 的代码都不需要改动**，完全向后兼容。

### 3.5 存档格式

```json
{
  "saveVersion": "3.0.2",
  "gameVersion": "3.0.2",
  "saveTime": "2026-08-22T10:00:00.000Z",
  "player": { /* 玩家60+字段 */ },
  "subsystems": {
    "inventory": { /* 背包数据 */ },
    "worldState": { /* 世界状态 */ },
    "npcStates": { /* NPC状态 */ }
  }
}
```

旧存档格式（扁平结构）在迁移时自动重组为新格式。

## 五、风险与应对

| 风险 | 应对 |
|------|------|
| 旧存档加载失败 | 保留Player.load()作为fallback，GameState加载失败时回退 |
| 字段代理性能损耗 | 仅在save/load时用代理，运行时直接访问Player属性 |
| 迁移逻辑遗漏 | 每个迁移函数写单元测试，版本跳跃测试 |
| 子系统状态不同步 | 子系统注册时强制实现getSaveData/loadSaveData接口 |
