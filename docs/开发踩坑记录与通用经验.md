# 项目开发踩坑记录与通用经验

> 记录开发过程中遇到的各种坑和解决方案，作为团队知识库，避免重复踩坑。
> 最后更新：2026-08-13

---

## 一、JavaScript 代码质量类

### 1. 全局变量命名不统一

**坑**：同一个东西有多个名字，有的地方叫 `InventorySystem`，有的地方叫 `Inventory`，导致调用时报 `is not defined` 错误。

**场景**：猎魔行动点击后游戏崩溃，报错 `InventorySystem is not defined`。

**根因**：重构时改了全局变量名，但漏改了几处调用。

**解决方案**：
- 全局变量名统一，一个概念只用一个名字
- 重构后全局搜索所有旧名称，确保全部替换
- 重要的全局变量在文件顶部统一声明注释

**预防措施**：
```javascript
// 全局变量命名约定：
// - 系统类用 System 后缀：TimeSystem, QuestSystem, MapSystem
// - 管理器类用 Manager 后缀：DataManager
// - 单例对象直接用名词：Player, Inventory, UI
// 改名字前先全局搜索，确保所有引用都改到
```

---

### 2. 重复初始化/加载导致数据被覆盖

**坑**：A 函数里已经加载了数据，B 函数里又加载一次，而且第二次加载的是空数据，把第一次的结果覆盖了。

**场景**：读档后背包物品全部丢失。

**根因**：
- `Player.load()` 里已经调用了 `Inventory.loadSaveData()` 加载背包
- `Game.continueGame()` 里又调用了一次 `Inventory.loadSaveData(Player.saveData?.inventory || [])`
- 但 `Player.saveData` 根本不存在，是 `undefined`，所以传入空数组 `[]`
- 刚加载好的背包被空数组覆盖了

**解决方案**：
- 谁负责加载数据要明确，不要重复加载
- 不要依赖不存在的对象属性（`Player.saveData` 根本没定义过）
- 重复加载前先想清楚："这步是不是已经做过了？"

**预防措施**：
- 单一职责原则：一个数据的加载只在一个地方做
- 加日志：加载数据时 console.log 一下，方便排查
- 代码 review 时重点看"初始化/加载"相关的逻辑

---

### 3. 硬编码的提示文字与实际逻辑不符

**坑**：UI 上写死了"完全恢复"，但实际逻辑根据睡觉时间恢复 80%~100%，玩家看到提示和实际不符。

**场景**：休息到明天，弹窗说"HP和MP完全恢复了"，但实际只恢复了80%。

**根因**：写代码时先写了提示文字，后来加了晚睡惩罚机制，但忘了改提示。

**解决方案**：
- 提示文字要根据实际状态动态生成，不要硬编码
- 改逻辑时顺便检查相关的 UI 提示有没有同步改

**预防措施**：
```javascript
// 不好的写法：硬编码
UI.showMessage('休息了一晚，HP 和 MP 完全恢复了！');

// 好的写法：根据实际状态动态生成
if (ratio >= 1.0) {
    UI.showMessage('休息了一晚，HP、MP 和体力完全恢复了！');
} else {
    UI.showMessage(`休息了一晚，恢复了 ${percent}%（熬夜效果较差）`);
}
```

## 二、UI 交互类

### 4. 弹窗点击穿透

**坑**：点击弹窗关闭后，鼠标抬起时会触发下面的按钮，导致意外操作。

**场景**：点击弹窗中间关闭，结果穿透到下面的"休息"按钮，无限休息循环。

**根因**：
- mousedown 在弹窗上触发，关闭弹窗
- mouseup 时弹窗已经消失，事件落到了下面的按钮上
- 下面的按钮触发了 click 事件

**解决方案（多层防护）**：
1. **z-index 足够高**：弹窗 z-index 至少 99999，遮罩 blocker 更高
2. **关闭时插入 blocker 遮罩**：关闭弹窗后立即创建一个全屏透明遮罩，800ms 后移除，挡住 mouseup 事件
3. **阻止事件冒泡和默认行为**：`preventDefault()` + `stopPropagation()` + `stopImmediatePropagation()`
4. **多个事件都阻止**：mousedown / mouseup / click / touchstart / touchend 都要阻止

**代码模板**：
```javascript
const closeMessage = () => {
    // 1. 先创建 blocker（在最顶层）
    const blocker = document.createElement('div');
    blocker.style.cssText = `
        position: fixed; top: 0; left: 0;
        width: 100%; height: 100%;
        z-index: 9999999;
        background: transparent;
    `;
    // 2. 阻止所有事件
    const stopEvent = (e) => {
        e.preventDefault();
        e.stopPropagation();
        e.stopImmediatePropagation();
    };
    blocker.addEventListener('mousedown', stopEvent);
    blocker.addEventListener('mouseup', stopEvent);
    blocker.addEventListener('click', stopEvent);
    blocker.addEventListener('touchstart', stopEvent);
    blocker.addEventListener('touchend', stopEvent);
    document.body.appendChild(blocker);
    
    // 3. 再移除弹窗
    overlay.remove();
    msgBox.remove();
    
    // 4. 一段时间后移除 blocker
    setTimeout(() => blocker.remove(), 800);
};
```

**经验值**：
- z-index 不要省，能多高就多高
- blocker 时间不要太短，500ms 不够，800ms 比较保险
- 点击弹窗外区域关闭比点击弹窗内关闭更不容易穿透

---

### 5. 事件选项的 action 漏处理

**坑**：对话选项有 `action: "back"`，但代码里只处理了 `start_battle` / `open_shop` / `close_dialogue` 三种，漏掉了最常用的 `back`，导致点击"告辞"没反应。

**场景**：和 NPC 聊天点击"告辞"没有效果，一直卡在对话界面。

**根因**：
- 选项同时设置了 `next: "default"` 和 `action: "back"`
- 代码只处理了 next 跳转，没处理 back action
- 点击后只是跳回默认对话节点，永远不会退出

**解决方案**：
- 处理 action 时，先判断是不是退出类动作（back / close_dialogue），是就直接退出
- 不要同时设置 next 和退出类 action，二者互斥

**预防措施**：
- 新增 action 类型时，先搜一下所有处理 action 的地方，确保都处理到
- 最基础的退出/返回功能要最先测试

## 三、游戏设计类

### 6. 随机事件概率设置不合理导致功能看似失效

**坑**：采集草药只有 40% 概率触发事件，60% 概率什么都不发生，玩家以为功能坏了。

**场景**：玩家连续两次采集草药，背包里什么都没有，任务进度 0/5，以为是 bug。

**根因**：
- 设计时想的是"40%概率触发特殊事件，额外获得草药"
- 但基础产出忘了加，导致 60% 概率什么都没有
- 玩家体验就是"这个功能坏了"

**解决方案**：
- 任何有产出的行动，都要有**基础产出**（保底）
- 随机事件是**额外奖励**，不是唯一产出途径
- 概率不要太低，至少让玩家第一次就能看到效果

**设计原则**：
```
基础产出（100%概率）+ 随机奖励（X%概率）
而不是
随机产出（X%概率）+ 什么都没有（1-X%概率）
```

**经验值**：
- 玩家第一次使用某个功能时，如果什么都没发生，他会认为功能坏了
- 保底机制很重要，不要让玩家脸黑到怀疑人生

---

### 7. 时间跳跃没有明显提示，玩家以为是 bug

**坑**：凌晨 3 点强制昏睡机制，玩家深夜探索 2 小时，时间从 01:00 跳到第二天 06:00，玩家以为是逃跑导致的 bug。

**场景**：战斗逃跑后，发现时间过了 29 小时，玩家以为是逃跑 bug。

**根因**：
- 强制昏睡机制是设计如此，但提示不明显
- 玩家不知道有这个机制，突然时间跳跃就以为是 bug

**解决方案**：
- 强制昏睡时要有明显的全屏提示，告诉玩家"你熬夜太久，昏过去了..."
- 深夜行动前可以有警告提示
- 重要的机制要让玩家知道，不要藏着掖着

## 四、存档系统类

### 8. 存档迁移容易遗漏字段

**坑**：版本更新加了新字段，旧存档迁移时没补全，导致读档后缺东西。

**场景**：新增召唤系技能后，旧存档读出来没有召唤系初始技能。

**解决方案**：
- 迁移函数里要补全新字段的默认值
- 技能、装备等可以根据当前等级反向推算应该有哪些，然后补全
- 存档版本号要跟上，每次改存档格式都升版本号

**迁移检查清单**：
- [ ] 新增的玩家属性有没有默认值？
- [ ] 新增的技能有没有根据等级补全？
- [ ] 新增的系统（装备强化、召唤兽等）有没有初始化？
- [ ] 旧存档的字段名变更有没有映射？

---

### 9. 存档加载顺序问题

**坑**：A 系统依赖 B 系统的数据，但 B 系统还没加载完，A 就先加载了，导致报错。

**解决方案**：
- 明确加载顺序：基础数据 → 玩家数据 → 各系统数据 → UI 渲染
- 不要在系统初始化时就依赖其他系统的存档数据
- 加载失败要有降级方案，不要直接崩溃

## 五、通用经验

### 10. 改 bug 先想"为什么会发生"，不要只改表面

**好的流程**：
1. 复现 bug
2. 找到根本原因
3. 想清楚为什么会出现这个问题（是漏改？是设计问题？是测试没覆盖？）
4. 修复 bug
5. 顺便检查有没有其他类似的问题
6. 记录到踩坑文档里，避免以后再犯

**不好的流程**：
1. 看到报错
2. 改一行代码
3. 提交，完事
4. 过几天又在别的地方出现同样的问题

---

### 11. 偶发 bug 要记录复现场景，不要只说"偶发"

**记录模板**：
- 做了什么操作（具体到点了哪个按钮）
- 之前的状态（等级、地点、HP/MP、有什么 buff/debuff）
- 报错信息（完整的错误栈）
- 出现频率（10次里出现几次）
- 有没有规律（比如只在深夜出现？只在特定敌人身上出现？）

**经验值**：
- 偶发 bug 90% 都是有规律的，只是还没找到
- 记录越详细，定位越快
- 不要轻易说"修好了"，偶发 bug 要多测几次确认

---

### 12. 测试要从玩家视角，不要从开发者视角

**开发者视角的测试**：
- "这个功能我写了，应该能用"
- "点一下，有反应，没问题"
- "边界情况？应该不会有人这么玩吧"

**玩家视角的测试**：
- "第一次玩，我知道该做什么吗？"
- "点了没反应，是我操作错了还是游戏坏了？"
- "这个数字是什么意思？我需要关心吗？"
- "玩了10分钟，我觉得有意思吗？"

**经验值**：
- 开发者自己测不出来的 bug，玩家一玩就出来
- 新手引导很重要，不要假设玩家知道你设计的所有机制

## 六、工具链类

### 13. 提交前一定要做语法检查

**坑**：少写了个括号，提交后玩家打开游戏白屏。

**解决方案**：
- 提交前 `node --check` 一下所有改过的 js 文件
- 重要的提交最好本地跑一下测试

---

### 14. Git commit message 要写清楚改了什么

**不好的 message**：`修复bug`、`优化`、`更新`、`wip`

**好的 message**：`Bug修复：采集草药添加基础产出，60%概率什么都没有的问题`

**经验值**：
- 写清楚改了什么、为什么改，以后查历史的时候会感谢自己
- 一个 commit 只做一件事，不要把一堆不相关的改动塞到一个 commit 里

---

### 15. 状态修饰符"计算了但没使用"的典型Bug模式

**坑**：写了一个通用函数计算所有状态修饰符（attackMod、defenseMod、speedMod等），攻击修饰符在伤害计算里用上了，但防御修饰符忘了用，导致所有防御降低/提升效果都是摆设。

**场景**：第八轮代码审查发现，黑畜妖的"恐惧尖叫"（防御-6）、超导反应的防御降低等效果完全不生效。

**根因**：
- `getStatusModifiers()` 函数正确计算了 `attackMod` 和 `defenseMod`
- 伤害计算时，攻击方用了 `attack + attackerMods.attackMod` ✅
- 但防御方直接用了 `target.defense`，忘了加 `targetMods.defenseMod` ❌
- 三个地方都漏了：玩家普攻、敌人普攻、技能攻击

**为什么这种Bug容易漏测**：
1. 攻击降低效果玩家能感受到（自己打不动了），但防御降低效果玩家不容易直观感受到（伤害数字变化不明显）
2. 黑盒测试时，玩家不会精确计算伤害数字差几点
3. 代码看起来"应该没问题"，因为函数写了，效果也加上了，只是最后一步没接进去

**预防措施**：
```javascript
// 写状态修饰符时，成对检查：
// 1. 计算了 attackMod → 所有攻击伤害计算都用上了吗？
// 2. 计算了 defenseMod → 所有防御伤害计算都用上了吗？
// 3. 计算了 speedMod → 所有速度判定都用上了吗？

// 伤害计算模板（确保对称）：
const attackerMods = this.getStatusModifiers(attacker);
const targetMods = this.getStatusModifiers(target);
const damage = Math.max(1, 
    (attacker.attack + attackerMods.attackMod) 
    - (target.defense + targetMods.defenseMod)
);
```

**检查清单**：
- [ ] 新增状态效果类型时，检查所有用到该属性的计算点
- [ ] 攻击/防御/速度是三对，不要只加了攻击忘了防御
- [ ] 黑盒测试时，用调试工具精确对比伤害数字
- [ ] 代码审查时，grep 所有 `defense` 出现的地方，看哪些地方应该加修饰符

---

### 16. 浏览器工具超时时，代码审查是有效的替代方案

**场景**：第八轮测试时浏览器自动化工具超时，无法进行黑盒点击测试。

**经验**：
- 深度代码审查（白盒测试）能发现黑盒测试发现不了的逻辑Bug
- 黑盒测试只能发现"点了没反应"，代码审查能发现"效果定义了但没生效"
- 两种测试方式互补：代码审查找逻辑Bug，黑盒测试找交互/UI Bug
- 关键路径要逐行跟踪：从技能定义 → 状态施加 → 修饰符计算 → 伤害应用，整条链路走一遍

**代码审查重点跟踪链路**：
1. 数据定义（skills.js/enemies.js）→ 效果类型对不对？
2. 状态施加（battle.js applyEffect）→ 有没有正确加到statusEffects？
3. 修饰符计算（getStatusModifiers）→ 有没有正确累加？
4. 实际应用（伤害计算/回合判定）→ 计算出来的值有没有用上？
5. UI显示 → 玩家能不能看到效果？

## 结语

踩坑不可怕，可怕的是同一个坑踩两次。

把每次踩的坑都记录下来，分析原因，总结经验，团队整体水平就会越来越高。
