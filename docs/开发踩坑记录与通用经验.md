# 项目开发踩坑记录与通用经验

> 记录开发过程中遇到的各种坑和解决方案，作为团队知识库，避免重复踩坑。
> 最后更新：2026-08-22

---

## 2026-08-22 NPC列表位置过滤bug（v2.9.3）

### 问题现象
- 新建游戏后点击"找人聊天"，提示"这里现在没有人..."
- 所有NPC都被位置过滤逻辑过滤掉了

### 根本原因
- `showNPCList`方法中假设`npcs`数组存储的是NPC的ID字符串
- 但实际传入的`npcs`数组存储的是**完整的NPC对象**（包含id、name、elements等字段）
- 代码执行`DataCharacters[npcId]`时，`npcId`是一个对象而不是字符串
- `DataCharacters[object]`永远返回`undefined`，导致所有NPC都被过滤掉

### 解决方案
- 兼容两种格式：如果`npcItem`是字符串，用`DataCharacters[npcItem]`查找；如果是对象，直接使用
- 添加详细调试信息帮助定位（打印每个NPC的name、location、是否匹配）
- 保留安全回退机制：过滤后无NPC时回退显示全部

### 经验教训
- **不要假设数据格式**：数组参数可能是字符串ID，也可能是完整对象，必须兼容两种格式
- **添加类型检查**：处理数组参数时，先检查元素类型，再决定如何处理
- **调试信息要详细**：遇到过滤类bug时，打印每个元素的关键字段（id、name、location），快速定位问题
- **安全回退很重要**：过滤类功能必须有回退机制，避免过滤掉所有内容导致功能不可用

## 2026-08-22 NPC详情页growthState未定义错误（v2.9.3）

### 问题现象
- 点击NPC详情按钮，控制台报错`Uncaught ReferenceError: growthState is not defined`
- 详情页无法正常显示

### 根本原因
- `showNPCDetail`方法中使用了`growthState`变量，但该变量在方法中没有定义
- 方法中定义的是`duelData`变量（通过`NPCGrowthService.getDuelData`获取）
- 代码中误用了`growthState`而不是`duelData`

### 解决方案
- 将`growthState`替换为`duelData`
- 详情页描述优先使用`duelData.description`，其次使用`npc.description`

### 经验教训
- **变量名要一致**：复制粘贴代码时，注意变量名是否需要修改
- **代码审查要仔细**：提交前检查是否有未定义的变量引用
- `node --check`只能检查语法错误，不能检查未定义变量，需要手动审查或使用lint工具

## 2026-08-16 弹窗点击拦截器问题（v0.92.11-v0.92.18）

### 问题现象
- 弹窗（每日总结、NPC对话、事件与情报、休息菜单）的按钮点击无反应
- 弹窗关闭后快速点击其他地方不生效，需要等一段时间

### 根本原因
1. **全局点击拦截器叠加**：showMessage函数每次调用都创建新的点击拦截器，但没有先移除旧的，导致多个拦截器叠加
2. **其他弹窗未恢复点击**：showDailySummary、showNPCDialog、showEventsAndIntel、showRestMenu等弹窗函数没有调用_restoreClicks()，如果在showMessage后打开，拦截器还在
3. **延迟过长**：弹窗关闭后点击延迟500ms/200ms，影响体验

### 解决方案
1. showMessage添加新拦截器前先移除旧拦截器（v0.92.11）
2. 添加_restoreClicks辅助方法，统一移除所有拦截器（v0.92.10）
3. 所有弹窗函数开头调用_restoreClicks()（v0.92.17-v0.92.18）
4. 弹窗关闭后点击延迟从500ms/200ms缩短到50ms（v0.92.16）

### 经验教训
- **全局状态必须统一管理**：点击拦截器、pointer-events等全局状态，必须有统一的恢复方法
- **所有弹窗都要考虑拦截器**：任何创建overlay/dialog的函数，都要在开头恢复点击状态
- **延迟要短**：防止点击穿透的延迟不应超过50ms，否则影响体验

## 2026-08-16 地图自动解锁bug（v0.92.12-v0.92.13）

### 问题现象
- 新建角色只点了一次上课，就自动解锁了三步塔、女子学校、老榕树街区、地圣泉等地图

### 根本原因
- checkAutoUnlockLocations函数只检查了minLevel和minOpinion条件
- locations.js中的解锁条件使用了level、quest、questCompleted、requiredFlag、hasItem等多种格式
- 由于没检查这些条件，只要地点有unlockCondition且没有minLevel限制，就会被自动解锁

### 解决方案
- checkAutoUnlockLocations支持所有条件格式（minLevel/level、requiredQuest/quest/questCompleted、requiredFlag、hasItem、minOpinion）
- _checkUnlockCondition同样支持所有条件格式
- hasItem检查使用Inventory.hasItem（Player.hasItem不存在）
- 百草谷从非标准的unlockLevel+unlockQuest转换为标准unlockCondition格式

### 经验教训
- **条件格式要统一**：数据文件中的条件格式必须统一，否则检查函数容易遗漏
- **自动解锁要谨慎**：任何自动解锁逻辑都要严格检查所有条件，不能只检查部分

## 2026-08-16 任务自动接取导致节奏过快（v0.92.19）

### 问题现象
- 玩家反馈"什么都还没做，新生考核就来了，第一章就结束了"
- 游戏进程混乱，任务自动接取导致节奏过快

### 根本原因
- story-chapter.js中主线任务会自动接取（Player.acceptQuest）
- 新手引导消息说"已自动接取任务"，但实际上任务不应该自动接取

### 解决方案
- 主线任务不自动接取，改为提示玩家主动接取
- 新手引导消息修正为"新任务已解锁，点击菜单→任务查看并接取"
- 章节开始时提示新主线任务已解锁，玩家自行决定是否接取

### 经验教训
- **自由度优先**：任务不自动接取，让玩家自己决定节奏
- **提示要准确**：UI提示必须与实际逻辑一致，不能误导玩家

## 一、JavaScript 代码质量类

### 1. 全局变量命名不统一

**坑**：同一个东西有多个名字，有的地方叫 `InventorySystem`，有的地方叫 `Inventory`，导致调用时报 `is not defined` 错误。

**场景**：猎魔行动点击后游戏崩溃，报错 `InventorySystem is not defined`。

**根因**：重构时改了全局变量名，但漏改了几处调用。

**解决方案**：
- 全局变量名统一，一个概念只用一个名字
- 重构后全局搜索所有旧名称，确保全部替换
- 重要的全局变量在文件顶部统一声明注释

**预防措施**：
```javascript
// 全局变量命名约定：
// - 系统类用 System 后缀：TimeSystem, QuestSystem, MapSystem
// - 管理器类用 Manager 后缀：DataManager
// - 单例对象直接用名词：Player, Inventory, UI
// 改名字前先全局搜索，确保所有引用都改到
```

---

### 2. 重复初始化/加载导致数据被覆盖

**坑**：A 函数里已经加载了数据，B 函数里又加载一次，而且第二次加载的是空数据，把第一次的结果覆盖了。

**场景**：读档后背包物品全部丢失。

**根因**：
- `Player.load()` 里已经调用了 `Inventory.loadSaveData()` 加载背包
- `Game.continueGame()` 里又调用了一次 `Inventory.loadSaveData(Player.saveData?.inventory || [])`
- 但 `Player.saveData` 根本不存在，是 `undefined`，所以传入空数组 `[]`
- 刚加载好的背包被空数组覆盖了

**解决方案**：
- 谁负责加载数据要明确，不要重复加载
- 不要依赖不存在的对象属性（`Player.saveData` 根本没定义过）
- 重复加载前先想清楚："这步是不是已经做过了？"

**预防措施**：
- 单一职责原则：一个数据的加载只在一个地方做
- 加日志：加载数据时 console.log 一下，方便排查
- 代码 review 时重点看"初始化/加载"相关的逻辑

---

### 3. 硬编码的提示文字与实际逻辑不符

**坑**：UI 上写死了"完全恢复"，但实际逻辑根据睡觉时间恢复 80%~100%，玩家看到提示和实际不符。

**场景**：休息到明天，弹窗说"HP和MP完全恢复了"，但实际只恢复了80%。

**根因**：写代码时先写了提示文字，后来加了晚睡惩罚机制，但忘了改提示。

**解决方案**：
- 提示文字要根据实际状态动态生成，不要硬编码
- 改逻辑时顺便检查相关的 UI 提示有没有同步改

**预防措施**：
```javascript
// 不好的写法：硬编码
UI.showMessage('休息了一晚，HP 和 MP 完全恢复了！');

// 好的写法：根据实际状态动态生成
if (ratio >= 1.0) {
    UI.showMessage('休息了一晚，HP、MP 和体力完全恢复了！');
} else {
    UI.showMessage(`休息了一晚，恢复了 ${percent}%（熬夜效果较差）`);
}
```

## 二、UI 交互类

### 4. 弹窗点击穿透

**坑**：点击弹窗关闭后，鼠标抬起时会触发下面的按钮，导致意外操作。

**场景**：点击弹窗中间关闭，结果穿透到下面的"休息"按钮，无限休息循环。

**根因**：
- mousedown 在弹窗上触发，关闭弹窗
- mouseup 时弹窗已经消失，事件落到了下面的按钮上
- 下面的按钮触发了 click 事件

**解决方案（多层防护）**：
1. **z-index 足够高**：弹窗 z-index 至少 99999，遮罩 blocker 更高
2. **关闭时插入 blocker 遮罩**：关闭弹窗后立即创建一个全屏透明遮罩，800ms 后移除，挡住 mouseup 事件
3. **阻止事件冒泡和默认行为**：`preventDefault()` + `stopPropagation()` + `stopImmediatePropagation()`
4. **多个事件都阻止**：mousedown / mouseup / click / touchstart / touchend 都要阻止

**代码模板**：
```javascript
const closeMessage = () => {
    // 1. 先创建 blocker（在最顶层）
    const blocker = document.createElement('div');
    blocker.style.cssText = `
        position: fixed; top: 0; left: 0;
        width: 100%; height: 100%;
        z-index: 9999999;
        background: transparent;
    `;
    // 2. 阻止所有事件
    const stopEvent = (e) => {
        e.preventDefault();
        e.stopPropagation();
        e.stopImmediatePropagation();
    };
    blocker.addEventListener('mousedown', stopEvent);
    blocker.addEventListener('mouseup', stopEvent);
    blocker.addEventListener('click', stopEvent);
    blocker.addEventListener('touchstart', stopEvent);
    blocker.addEventListener('touchend', stopEvent);
    document.body.appendChild(blocker);
    
    // 3. 再移除弹窗
    overlay.remove();
    msgBox.remove();
    
    // 4. 一段时间后移除 blocker
    setTimeout(() => blocker.remove(), 800);
};
```

**经验值**：
- z-index 不要省，能多高就多高
- blocker 时间不要太短，500ms 不够，800ms 比较保险
- 点击弹窗外区域关闭比点击弹窗内关闭更不容易穿透

---

### 5. 事件选项的 action 漏处理

**坑**：对话选项有 `action: "back"`，但代码里只处理了 `start_battle` / `open_shop` / `close_dialogue` 三种，漏掉了最常用的 `back`，导致点击"告辞"没反应。

**场景**：和 NPC 聊天点击"告辞"没有效果，一直卡在对话界面。

**根因**：
- 选项同时设置了 `next: "default"` 和 `action: "back"`
- 代码只处理了 next 跳转，没处理 back action
- 点击后只是跳回默认对话节点，永远不会退出

**解决方案**：
- 处理 action 时，先判断是不是退出类动作（back / close_dialogue），是就直接退出
- 不要同时设置 next 和退出类 action，二者互斥

**预防措施**：
- 新增 action 类型时，先搜一下所有处理 action 的地方，确保都处理到
- 最基础的退出/返回功能要最先测试

## 三、游戏设计类

### 6. 随机事件概率设置不合理导致功能看似失效

**坑**：采集草药只有 40% 概率触发事件，60% 概率什么都不发生，玩家以为功能坏了。

**场景**：玩家连续两次采集草药，背包里什么都没有，任务进度 0/5，以为是 bug。

**根因**：
- 设计时想的是"40%概率触发特殊事件，额外获得草药"
- 但基础产出忘了加，导致 60% 概率什么都没有
- 玩家体验就是"这个功能坏了"

**解决方案**：
- 任何有产出的行动，都要有**基础产出**（保底）
- 随机事件是**额外奖励**，不是唯一产出途径
- 概率不要太低，至少让玩家第一次就能看到效果

**设计原则**：
```
基础产出（100%概率）+ 随机奖励（X%概率）
而不是
随机产出（X%概率）+ 什么都没有（1-X%概率）
```

**经验值**：
- 玩家第一次使用某个功能时，如果什么都没发生，他会认为功能坏了
- 保底机制很重要，不要让玩家脸黑到怀疑人生

---

### 7. 时间跳跃没有明显提示，玩家以为是 bug

**坑**：凌晨 3 点强制昏睡机制，玩家深夜探索 2 小时，时间从 01:00 跳到第二天 06:00，玩家以为是逃跑导致的 bug。

**场景**：战斗逃跑后，发现时间过了 29 小时，玩家以为是逃跑 bug。

**根因**：
- 强制昏睡机制是设计如此，但提示不明显
- 玩家不知道有这个机制，突然时间跳跃就以为是 bug

**解决方案**：
- 强制昏睡时要有明显的全屏提示，告诉玩家"你熬夜太久，昏过去了..."
- 深夜行动前可以有警告提示
- 重要的机制要让玩家知道，不要藏着掖着

## 四、存档系统类

### 8. 存档迁移容易遗漏字段

**坑**：版本更新加了新字段，旧存档迁移时没补全，导致读档后缺东西。

**场景**：新增召唤系技能后，旧存档读出来没有召唤系初始技能。

**解决方案**：
- 迁移函数里要补全新字段的默认值
- 技能、装备等可以根据当前等级反向推算应该有哪些，然后补全
- 存档版本号要跟上，每次改存档格式都升版本号

**迁移检查清单**：
- [ ] 新增的玩家属性有没有默认值？
- [ ] 新增的技能有没有根据等级补全？
- [ ] 新增的系统（装备强化、召唤兽等）有没有初始化？
- [ ] 旧存档的字段名变更有没有映射？

---

### 9. 存档加载顺序问题

**坑**：A 系统依赖 B 系统的数据，但 B 系统还没加载完，A 就先加载了，导致报错。

**解决方案**：
- 明确加载顺序：基础数据 → 玩家数据 → 各系统数据 → UI 渲染
- 不要在系统初始化时就依赖其他系统的存档数据
- 加载失败要有降级方案，不要直接崩溃

## 五、通用经验

### 10. 改 bug 先想"为什么会发生"，不要只改表面

**好的流程**：
1. 复现 bug
2. 找到根本原因
3. 想清楚为什么会出现这个问题（是漏改？是设计问题？是测试没覆盖？）
4. 修复 bug
5. 顺便检查有没有其他类似的问题
6. 记录到踩坑文档里，避免以后再犯

**不好的流程**：
1. 看到报错
2. 改一行代码
3. 提交，完事
4. 过几天又在别的地方出现同样的问题

---

### 11. 偶发 bug 要记录复现场景，不要只说"偶发"

**记录模板**：
- 做了什么操作（具体到点了哪个按钮）
- 之前的状态（等级、地点、HP/MP、有什么 buff/debuff）
- 报错信息（完整的错误栈）
- 出现频率（10次里出现几次）
- 有没有规律（比如只在深夜出现？只在特定敌人身上出现？）

**经验值**：
- 偶发 bug 90% 都是有规律的，只是还没找到
- 记录越详细，定位越快
- 不要轻易说"修好了"，偶发 bug 要多测几次确认

---

### 12. 测试要从玩家视角，不要从开发者视角

**开发者视角的测试**：
- "这个功能我写了，应该能用"
- "点一下，有反应，没问题"
- "边界情况？应该不会有人这么玩吧"

**玩家视角的测试**：
- "第一次玩，我知道该做什么吗？"
- "点了没反应，是我操作错了还是游戏坏了？"
- "这个数字是什么意思？我需要关心吗？"
- "玩了10分钟，我觉得有意思吗？"

**经验值**：
- 开发者自己测不出来的 bug，玩家一玩就出来
- 新手引导很重要，不要假设玩家知道你设计的所有机制

**坑**：少写了个括号，提交后玩家打开游戏白屏。

**解决方案**：
- 提交前 `node --check` 一下所有改过的 js 文件
- 重要的提交最好本地跑一下测试

### 14. Git commit message 要写清楚改了什么

**不好的 message**：`修复bug`、`优化`、`更新`、`wip`

**好的 message**：`Bug修复：采集草药添加基础产出，60%概率什么都没有的问题`

**经验值**：
- 写清楚改了什么、为什么改，以后查历史的时候会感谢自己
- 一个 commit 只做一件事，不要把一堆不相关的改动塞到一个 commit 里

### 15. 状态修饰符"计算了但没使用"的典型Bug模式

**坑**：写了一个通用函数计算所有状态修饰符（attackMod、defenseMod、speedMod等），攻击修饰符在伤害计算里用上了，但防御修饰符忘了用，导致所有防御降低/提升效果都是摆设。

**场景**：第八轮代码审查发现，黑畜妖的"恐惧尖叫"（防御-6）、超导反应的防御降低等效果完全不生效。

**根因**：
- `getStatusModifiers()` 函数正确计算了 `attackMod` 和 `defenseMod`
- 伤害计算时，攻击方用了 `attack + attackerMods.attackMod` ✅
- 但防御方直接用了 `target.defense`，忘了加 `targetMods.defenseMod` ❌
- 三个地方都漏了：玩家普攻、敌人普攻、技能攻击

**为什么这种Bug容易漏测**：
1. 攻击降低效果玩家能感受到（自己打不动了），但防御降低效果玩家不容易直观感受到（伤害数字变化不明显）
2. 黑盒测试时，玩家不会精确计算伤害数字差几点
3. 代码看起来"应该没问题"，因为函数写了，效果也加上了，只是最后一步没接进去

**预防措施**：
```javascript
// 写状态修饰符时，成对检查：
// 1. 计算了 attackMod → 所有攻击伤害计算都用上了吗？
// 2. 计算了 defenseMod → 所有防御伤害计算都用上了吗？
// 3. 计算了 speedMod → 所有速度判定都用上了吗？

// 伤害计算模板（确保对称）：
const attackerMods = this.getStatusModifiers(attacker);
const targetMods = this.getStatusModifiers(target);
const damage = Math.max(1, 
    (attacker.attack + attackerMods.attackMod) 
    - (target.defense + targetMods.defenseMod)
);
```

**检查清单**：
- [ ] 新增状态效果类型时，检查所有用到该属性的计算点
- [ ] 攻击/防御/速度是三对，不要只加了攻击忘了防御
- [ ] 黑盒测试时，用调试工具精确对比伤害数字
- [ ] 代码审查时，grep 所有 `defense` 出现的地方，看哪些地方应该加修饰符

## 2026-08-20 "Script error. (第0行)"与初始化顺序问题（v2.7.11）

### 问题现象
- 浏览器端触发任何战斗都报错："游戏出错: Script error. (第0行)"
- 自动化测试（node环境）118通过/0失败，完全测不出问题
- debug面板按钮点击无响应（后来发现是被战斗错误的全局异常处理干扰）

### 为什么修复花了很久——4个刁钻问题叠加

#### 1. 错误信息被浏览器完全屏蔽
"Script error. (第0行)"是浏览器跨域安全策略的产物：当错误发生在不同"源"的脚本中时，浏览器会屏蔽真实的错误消息和堆栈，只显示这一行。本地file://协议下也可能触发。

**走的弯路**：
- 先用`UI.showMessage()`加调试点，但UI.showMessage本身是异步模态对话框，会阻塞代码执行，调试点显示到第1个就停了，误以为是后面代码出错
- 再用`alert()`加调试点，alert是同步阻塞的，更严重——点击按钮后alert没弹出来，误以为是事件绑定有问题，花了大量时间排查事件面板的按钮onclick绑定
- 最后才想到：**在try-catch里创建一个div直接把error.message和error.stack写在页面顶部**，一秒就拿到了真实错误：`Cannot read properties of null (reading 'talents')` at talent-combat.js:49

#### 2. 根本原因隐蔽——"使用先于初始化"
拿到堆栈后定位到`BattleSystem.startBattle`：
- 第590行调用 `TalentCombatSystem.init(this.player)`
- 但`this.player`在第828行才赋值初始化
- 中间第710行（恐惧系统）、第740行（暴躁之泉）也都在用`this.player`

**为什么这种问题容易漏**：
- 代码是逐步迭代出来的，早期`this.player`可能在方法开头就初始化了，后来某次重构把初始化块移到了后面（为了和天赋加成、疲劳减益放一起），但前面已经有3处使用点
- node自动化测试里，战斗测试可能直接构造了player对象或mock了BattleSystem，没有走完整的startBattle初始化路径
- 代码审查时，看到`this.player = {...}`就以为初始化了，不会去检查它上面是否已经有使用点

#### 3. 调试代码本身引入新问题
- 加了6个alert + 3个UI.showMessage调试点，这些代码本身可能改变执行时序
- alert阻塞事件循环，导致setTimeout里的回调不执行，进一步误导排查方向
- 清理调试代码时差点漏删，需要逐行检查

#### 4. 全局错误处理掩盖了真实堆栈
游戏有全局`window.onerror`处理，捕获异常后显示"游戏出错: Script error."，但没有把error对象的详细信息打出来。如果全局错误处理能直接console.error完整error对象，F12控制台就能看到堆栈，不用绕这么大弯。

### 解决方案
1. **battle.js**：将`this.player`初始化块（含天赋属性加成、疲劳减益）整体上移到`this.enemy`初始化之后，确保所有使用点之前已初始化
2. **talent-combat.js**：`init(player)`添加null检查，player为null时回退到全局`Player`对象
3. **game.js**：`lastBattle`移除`JSON.parse(JSON.stringify())`深拷贝，避免潜在的循环引用风险

### 经验沉淀

#### 【调试方法论】浏览器端"Script error. (第0行)"标准处理流程
```
1. 不要用alert/UI.showMessage调试——它们会阻塞执行，误导方向
2. 直接在可疑代码块外包try-catch，catch里创建div显示error.message+error.stack
3. 如果全局有onerror处理，临时改成console.error完整error对象
4. 拿到真实堆栈后，Grep定位对象的所有赋值点，确认初始化顺序
```

- [ ] 重构移动代码块时，检查该块依赖的变量是否也一起移动了

## 2026-08-20 临时初始化值未被正确覆盖——觉醒系别变成火系（v2.8.1）

### 问题现象
- 玩家创建角色时选择治愈系（或其他非火系），但进入游戏后UI显示、战斗系统、技能列表都显示为火系
- 玩家面板显示"火系"，战斗中只能使用火系技能，治愈系技能完全不可用
- 重新创建角色选择冰系/雷系等，结果都变成火系

### 根本原因——"只改了显示字段，没改数据源"

代码中有两个相关字段：
1. `Player.element` —— 一个简单的字符串字段，几乎没被系统使用
2. `Player.elements` —— 数组字段，**所有系统实际使用的数据源**（UI显示、战斗技能、经验分配、天赋系统都用`elements[0]`）

创建角色时的流程：
1. `Player.init(name, 'fire')` —— 临时用火系初始化，`elements = ['fire']`
2. 玩家选择天生天赋后，如果天赋绑定系别，设置 `Player.element = talent.boundElement`
3. 如果是普通天赋，玩家在系别选择界面选治愈系，设置 `Player.element = 'heal'`
4. **但两处都只设置了`Player.element`，没有更新`Player.elements`数组！**
5. 所以`elements`仍然是`['fire']`，所有系统都读取`elements[0]`即'fire'

### 为什么这种问题容易漏

1. **字段命名误导**：`element`（单数）和`elements`（复数）看起来像同一个东西的不同形式，实际上一个是遗留字段、一个是真实数据源
2. **临时初始化的注释**：代码里写了"临时用fire初始化，后续会被天赋或选择覆盖"，开发者以为覆盖了就完事了，没仔细检查覆盖的是哪个字段
3. **UI显示可能用了`element`**：如果某些地方显示用的是`element`，就会出现"显示是治愈系，但战斗是火系"的分裂现象，更难排查
4. **自动化测试覆盖不到**：测试用例可能直接构造`elements`数组，不会走完整的创建角色→天赋选择→系别选择流程

### 解决方案

在两处设置`Player.element`的地方，同步更新`Player.elements`数组、`elementLevels`和`elementExp`：

```javascript
// confirmInnateTalent 中绑定系天赋的情况
Player.element = talent.boundElement;
Player.elements = [talent.boundElement];  // 替换整个数组，因为这是第一系
Player.elementLevels[talent.boundElement] = 1;
Player.elementExp[talent.boundElement] = 0;

// selectElementAfterTalent 中玩家选择系别的情况
Player.element = element;
Player.elements = [element];  // 替换整个数组
Player.elementLevels[element] = 1;
Player.elementExp[element] = 0;
```

### 经验沉淀

- [ ] 临时初始化的字段，后续覆盖时是否覆盖了**所有**相关字段？

- [ ] 主数据源和派生/显示字段是否同步？

#### 【架构建议】消除遗留字段
- 如果`Player.element`已经不再被系统使用，应该直接删除或标记为`@deprecated`
- 或者在`element`的setter中自动同步`elements`，避免手动维护两个字段

## 2026-08-20 弹窗覆盖innerHTML导致黑屏（v2.8.3）

### 问题现象

玩家在角色信息界面点击系别天赋查看详情，关闭弹窗后整个游戏界面黑屏，什么内容都没有了。治愈系角色必现，其他系别也可能出现。

### 根本原因

天赋详情弹窗和主副修选择弹窗使用了错误的DOM注入方式：

```javascript
// ❌ 错误：赋值覆盖，会完全替换gameContainer的所有内容
this.elements.gameContainer.innerHTML = `
    <div id="talent-detail-overlay" ...>
```

而技能详情弹窗和敌人详情弹窗使用的是正确的方式：

```javascript
// ✅ 正确：追加，在原有内容上叠加弹窗
this.elements.gameContainer.innerHTML += `
    <div id="skill-detail-overlay" ...>
```

当使用`=`赋值时，`gameContainer`中原有的所有DOM元素（包括角色面板、地图、UI等）被完全替换为只有弹窗的内容。关闭弹窗时虽然`remove()`了弹窗元素，但原有内容已经被覆盖丢失了，所以就黑屏了。

### 为什么这种问题容易漏

1. **`=`和`+=`视觉差异极小**：代码审查时很容易忽略这一个字符的差别
2. **弹窗功能正常**：弹窗本身能正常显示和关闭，开发者测试时可能只关注弹窗内容是否正确，没注意关闭后原界面是否恢复
3. **自动化测试覆盖不到**：node环境下没有真实DOM，测试不会检测innerHTML赋值方式
4. **部分弹窗正确部分错误**：如果同一批开发的弹窗中有些用了`+=`有些用了`=`，更容易混淆

### 解决方案

将所有弹窗类的`gameContainer.innerHTML =`改为`gameContainer.innerHTML +=`：

```javascript
// 天赋详情弹窗
this.elements.gameContainer.innerHTML += `
    <div id="talent-detail-overlay" ...>

// 主副修选择弹窗
this.elements.gameContainer.innerHTML += `
    <div id="ps-selection-overlay" ...>
```

- [ ] 新弹窗实现时，参考已有的正确弹窗（如技能详情/敌人详情）的写法

### 17. 数据定义了效果，但战斗代码没有处理逻辑

**坑**：技能数据里定义了 `healing_reduction`（治疗降低/坏血效果），状态效果也能正确施加到目标身上，但所有治疗/恢复代码都没有检查这个状态，导致效果名存实亡。

// 新增状态效果类型时的检查清单：
// 1. 数据定义 ✓
// 2. 状态施加 ✓
// 3. 状态显示（UI tooltip）✓
// 4. 实际效果代码 ← 最容易忘！

### 18. 行动锁/状态标志位忘记重置导致战斗卡死

**坑**：自动战斗时，`isProcessingAction` 标志在玩家行动开始时设为true防止重复点击，但在敌人回合结束时忘记重置为false，导致第二回合后自动战斗停止响应。

**场景**：开启自动战斗，第一回合正常打完，第二回合玩家角色站着不动，什么也不做。

**根因**：
- `_processPlayerTurn()` 中设置 `this.isProcessingAction = true`
- 正常流程：玩家行动 → endPlayerTurn → 敌人行动 → endEnemyTurn → 重置isPlayerTurn
- 但 `isProcessingAction` 只在 `_processPlayerTurn` 入口设置，没有在 `endEnemyTurn` 中重置
- 自动战斗的 `autoPlayerTurn()` 检查 `isProcessingAction`，发现还是true，就跳过了

**解决方案**：
- 在 `endEnemyTurn()` 中，进入玩家回合时重置 `this.isProcessingAction = false`
- 所有"锁"类标志位，都要在**逻辑对应的出口**重置，不要只在入口设置

**预防措施**：
```javascript
// 使用状态锁时的模式：
// 1. 定义锁：this.isProcessingAction = false
// 2. 入口加锁：this.isProcessingAction = true
// 3. 正常出口解锁：this.isProcessingAction = false
// 4. 异常出口解锁（catch/early return）：也要解锁！
// 5. 搜索所有设置锁=true的地方，确认每个都有对应的解锁点
```

**类似的锁**：
- isPlayerTurn（玩家回合标志）
- isCasting（引导中标志）
- active（战斗进行中标志）
- 任何防止重复点击的标志位

### 19. UI渲染重复拼接相同内容

**坑**：渲染战斗界面时，敌人状态效果列表在两个地方各渲染了一遍，导致同一个buff/debuff图标显示两次。

**场景**：敌人中了灼烧，UI上显示两个灼烧图标。

**根因**：
- renderBattleScreen中，状态效果渲染代码被复制粘贴了两次
- 第一次渲染了一组（简单版），第二次又渲染了一组（详细版带tooltip）
- 两组代码功能重叠，导致重复

**解决方案**：
- 删除重复的第一组，保留功能更完整的第二组
- 渲染代码不要复制粘贴，公共部分抽成函数

**预防措施**：
- 修改UI渲染代码时，先搜索是否已有相同功能的代码
- 复制粘贴代码后，立刻删除旧代码，不要留着"以防万一"
- 渲染函数保持单一职责：一个区域一个渲染函数

### 20. "自动吸收/自动触发"类功能要验证实际效果，不能只看日志

**坑**：小泥鳅坠自动吸收残魄的功能，日志显示"自动吸收了XXX残魄"，但实际上残魄还是进了背包，小泥鳅坠经验一点没涨。

**场景**：击杀妖魔后提示"小泥鳅坠自动吸收了独眼魔狼残魄"，但打开背包一看残魄还在，小泥鳅坠经验没变化。

**根因**：
- 代码里判断了"有小泥鳅坠"就显示吸收日志
- 但实际的经验增加逻辑写在了else分支里（没有小泥鳅坠才走的分支）
- 有小泥鳅坠时只打了日志，没有调用 `addExperience`

**解决方案**：
- 有小泥鳅坠时：直接给小泥鳅坠加经验，支持升级提示，满级时残魄才进背包
- 没有小泥鳅坠时：残魄进背包

**预防措施**：
```javascript
// 自动触发类功能的验证清单：
// 1. 触发条件正确吗？（有小泥鳅坠才触发）
// 2. 日志显示了吗？
// 3. 实际数值变化了吗？← 最容易只打日志不改数值！
// 4. 边界情况处理了吗？（满级后怎么办？经验溢出怎么办？）
// 5. 玩家能验证结果吗？（打开小泥鳅坠面板看经验涨了没）
```

**类似问题**：
- 自动战斗只打日志不行动
- 成就解锁只弹提示不记录
- 任务进度只更新UI不更新数据

## 代码审查快速检查清单

每次修改战斗系统代码后，快速过一遍：

- [ ] **语法检查**：`node --check` 所有改过的文件
- [ ] **状态效果**：新效果类型有没有在所有相关计算点处理？
- [ ] **锁/标志位**：加锁的地方有没有对应的解锁？
- [ ] **UI渲染**：有没有重复渲染？有没有遗漏渲染？
- [ ] **自动功能**：日志显示了，实际数值变了吗？
- [ ] **净化/清除**：新debuff有没有加到净化列表？
- [ ] **多段攻击**：统计数据（总伤害、暴击数、未命中数）是否正确累加？
- [ ] **治疗点**：所有治疗路径都经过getHealingMultiplier了吗？
- [ ] **MP消耗**：技能MP扣了吗？引导技能和即时技能的扣除位置一致吗？
- [ ] **回合结束**：checkBattleEnd在关键节点都调用了吗？
