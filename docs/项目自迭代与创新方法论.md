# 项目自迭代与创新方法论

> 本文档定义项目的自迭代机制、创新保护机制、玩家体验驱动开发原则。
> 最后更新：2026-09-09
> 核心原则：**方法论是脚手架，不是牢笼。方法论的存在是为了让创新更高效，而不是让创新更困难。**

---

## 一、为什么需要自迭代机制？

### 1.1 历史教训

v3.4-v3.13共10个版本的开发中，积累了18个问题：
- Git提交滞后10个版本
- 版本号多处不一致
- 文档导航缺失5个新系统
- Skill references 7个文件停留在v1.8.0
- L1测试2个警告长期未处理
- 代码中残留DEBUG注释和未完成TODO

**根因不是"不够努力"，而是"流程本身缺乏自净能力"**：
- 文档同步是软要求，没有硬验收
- 没有定期的项目健康度审计
- 方法论是"写出来的"，不是"用出来的"
- 权威来源不唯一，维护成本翻倍
- 创新与规范的张力没有被正视

### 1.2 自迭代机制的目标

1. **问题早发现** — 不要等问题积累10个版本才清理
2. **方法论持续改进** — 方法论不是一成不变的，要根据实际使用反馈持续优化
3. **创新有空间** — 规则不能捆住手脚，要给创新留出通道
4. **玩家体验优先** — 从"好玩"反向推导开发，而不是从"技术实现"正向推导

## 二、自迭代机制（按版本数量触发，适合agent快速开发）

### 2.1 每个版本发布后：版本反思会（强制，30分钟）

**触发时机**：每个版本（vX.Y.Z）发布并提交后，立即执行

**执行流程**：
```
1. 这个版本哪些做得好？（保留并沉淀为方法论）
2. 哪些做得不好？（记录问题，下版本改进）
3. 方法论哪里好用？哪里不好用？（记录方法论反馈）
4. 玩家体验如何？（黑盒测试反馈/自己玩的感受）
5. 下版本重点是什么？
→ 记录到 docs/version-reflection/vX.Y.Z_反思.md
```

**反思模板**：
```markdown
# vX.Y.Z 版本反思

> 发布日期：YYYY-MM-DD
> 版本主题：xxx

## 做得好的
- ...

## 做得不好的
- ...

## 方法论反馈
- 好用的：...
- 不好用的：...
- 建议改进：...

## 玩家体验
- ...

## 下版本重点
- ...
```

### 2.2 每5个版本：项目健康度审计（强制，1小时）

**触发时机**：每完成5个版本（如v3.15.0、v3.20.0、v3.25.0...），立即执行

**审计清单**：

#### 文档审计（20分钟）
- [ ] 版本号一致吗？（AGENTS/TODO/README/CHANGELOG/ui-title.js 5个位置）
- [ ] 文档导航有失效链接吗？（AGENTS.md导航表所有链接可访问）
- [ ] 数据统计准确吗？（README/AGENTS中的技能/妖魔/NPC/任务数量与实际一致）
- [ ] 新系统有设计文档吗？（每个新系统在docs/或version-design/中有对应文档）
- [ ] README更新了吗？（新功能介绍、数据统计）

#### 代码审计（20分钟）
- [ ] 有未完成的TODO吗？（grep "TODO"，确认每个都有上下文和计划）
- [ ] 有注释掉的DEBUG代码吗？（grep "//.*console\|//.*DEBUG"，清理无用代码）
- [ ] 测试通过吗？（node tests/run.js，0失败0警告）
- [ ] 有冗余代码吗？（重复的函数、未使用的变量）
- [ ] 语法检查通过吗？（node --check 所有修改的文件）

#### 方法论审计（15分钟）
- [ ] 哪些方法论在实际使用？（列出高频使用的）
- [ ] 哪些方法论已经过时？（内容与当前版本不符的）
- [ ] 哪些方法论需要新增？（开发中遇到的无方法论场景）
- [ ] 方法论有冗余吗？（重复内容的文档）

#### 创新审计（5分钟）
- [ ] 这5个版本有什么新玩法？
- [ ] 玩家反馈如何？（如果有）
- [ ] 有没有被规则捆住手脚的情况？
- [ ] 下5个版本的创新方向是什么？

**输出**：`docs/version-reflection/健康度审计_vX.Y.Z.md`，发现问题立即创建任务到TODO.md

### 2.3 每10个版本：方法论评审会（强制，2小时，需用户确认）

**触发时机**：每完成10个版本（如v3.20.0、v3.30.0...），立即执行

**评审流程**：
```
1. 回顾过去10个版本的方法论使用情况（来自版本反思会的反馈汇总）
2. 评审方法论改进提案（来自版本反思会和健康度审计的建议）
3. 决定哪些方法论保留/修改/废弃/新增
4. 检查创新空间是否足够（规则有没有太死？创新通道有没有在用？）
5. 检查玩家体验驱动原则是否落实
6. 向用户汇报评审结果，用户确认后执行方法论更新
→ 更新方法论，记录变更历史到 docs/version-reflection/方法论评审_vX.Y.Z.md
```

**评审原则**：
- 方法论不是越多越好，而是越有效越好
- 能用一条规则说清的，不写十条
- 能让agent自动执行的，不要求人工参与
- 每次评审至少删除1个过时或冗余的方法论

## 三、规则分层与创新保护机制

### 3.1 规则分层（明确哪些可以打破）

| 层级 | 内容 | 能否打破 | 说明 |
|------|------|---------|------|
| **铁律** | 玩家有自己的人生/人设不可破坏/小说驱动/数据驱动/设计先对齐再实施 | ❌ 不可违反 | 违反这些就是项目方向错误 |
| **规范** | 11步流程/文档同步/测试/代码规范/UI规范 | ⚠️ 可说明理由后打破 | 小创新可走快速通道，大改动必须走规范 |
| **建议** | 命名习惯/文档格式/具体实现方式 | ✅ 自由取舍 | 参考即可，不强制 |

### 3.2 快速创新通道（小功能/小玩法）

**适用场景**：加一个小事件/小对话/小机制/小优化，不涉及核心系统架构和UI大改

**流程**（简化版，不需要走完整11步）：
```
1. 有想法 → 2. 快速原型（直接写代码，不写完整设计文档）
→ 3. 自己玩一遍，觉得好玩 → 4. 跑测试（node tests/run.js）
→ 5. 补简短设计说明（3-5行，记录在对应version-design或代码注释中）
→ 6. 提交
```

**快速通道的边界**：
- ✅ 可以：加一个随机事件、加一段NPC对话、加一个小物品、调整数值
- ❌ 不可以：新系统架构、UI布局大改、核心战斗逻辑改动、影响存档兼容性的改动
- ❌ 不可以：违反铁律的任何改动

**如果不确定能不能走快速通道**：默认走完整规范流程，或先问用户。

### 3.3 创新实验机制

- 允许在debug模式下实验新玩法，不影响正式版本
- 实验结果好的，再走正式流程纳入正式版本
- 实验结果不好的，直接丢弃，不浪费时间写文档
- 实验代码可以不遵循代码规范，但纳入正式版本前必须重构

### 3.4 创新空间检查

每次方法论评审会必须检查：
- 过去10个版本中，快速创新通道用了几次？
- 有没有因为规则太死而放弃的创新想法？
- 有没有"为了遵循规范而做了不好玩的功能"？
- 下10个版本的创新方向是什么？

**如果连续10个版本没有使用快速创新通道**，说明规则太死，必须放松。

## 四、玩家体验驱动开发

### 4.1 每个功能设计前必须回答的3个问题

1. **玩家为什么要做这个？**
   - 动机是什么？（好奇心？成就感？收集欲？策略选择？）
   - 奖励是什么？（数值奖励？剧情奖励？社交奖励？）
   - 成就感来自哪里？（克服困难？发现秘密？成长感？）

2. **这个功能好玩在哪里？**
   - 是策略选择？（玩家需要做有意义的决策）
   - 是惊喜？（随机事件/意外发现）
   - 是成长感？（数值提升/能力增强）
   - 是叙事体验？（剧情沉浸/角色互动）
   - 还是只是机械操作？（如果是，必须改进或删除）

3. **小说原著中对应的内容是什么？**
   - 能不能从原著中挖掘更有趣的玩法？
   - 原著中这个场景的核心体验是什么？
   - 能不能把原著的"名场面"转化为玩家可参与的玩法？

**回答不了这3个问题的功能，不做。**

### 4.2 小说内容转化方法论（从"数据校准"升级到"玩法创新"）

#### 错误的转化方式
```
原著里有这个妖魔 → 加这个妖魔的数据（名字/血量/攻击）
原著里有这个事件 → 加这个事件的文本描述
原著里有这个NPC → 加这个NPC的对话
```
**问题**：只是"还原"，没有"转化"，玩家体验不到原著的核心乐趣。

#### 正确的转化方式
```
原著里这个妖魔的战斗方式很有趣 → 能不能做成一个独特的战斗机制？
  例：原著中"眼虫"可以寄生 → 做成"寄生debuff"机制，玩家需要想办法清除
原著里这个事件的选择很纠结 → 能不能做成一个有意义的玩家抉择？
  例：原著中"地圣泉名额"有争议 → 做成玩家可以挑战宇昂争取资格的玩法
原著里这个角色的性格很鲜明 → 能不能做成有独特互动方式的NPC？
  例：原著中"穆白"高傲 → 对话选项需要用实力或智慧才能赢得尊重
原著里这个修炼方式很特别 → 能不能做成独特的修炼玩法？
  例：原著中"闭关修炼" → 做成有特殊事件和走火入魔风险的长周期行为
```

**核心原则**：不是"还原原著"，而是"让玩家体验原著的核心乐趣"。

### 4.3 趣味性评估清单

每个功能完成后，自己玩一遍，回答：
- [ ] 我会主动想做这个功能吗？（还是只是因为有奖励才做？）
- [ ] 做这个功能的时候有期待感吗？（还是只是机械点击？）
- [ ] 结果有惊喜感吗？（还是完全 predictable？）
- [ ] 想再做一次吗？（还是做一次就够了？）
- [ ] 会想分享给朋友吗？（"你看我遇到了这个！"）

**如果5个问题中有3个以上答"否"，这个功能需要改进或删除。**
