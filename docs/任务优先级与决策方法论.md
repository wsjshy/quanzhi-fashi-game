# 任务优先级与决策方法论

> **版本**：v1.0
> **日期**：2026-09-10
> **适用场景**：当面临"先做A还是先做B"、"继续优化还是切换任务"等抉择时，使用本方法论自行决策，不需要询问用户。
> **核心原则**：决策可解释、可复用、可迭代。每次决策后记录结果，持续优化方法论。

---

## 一、为什么需要这套方法论

**问题**：开发过程中经常面临抉择：
- 当前功能核心已完成，是继续打磨细节还是切换到下一个大任务？
- 用户提了多个需求，先做哪个？
- 发现了技术债务，是现在还还是以后还？
- 测试发现了小问题，是现在修还是攒一波一起修？

**过去的做法**：每次都问用户，导致：
1. 用户负担重，需要频繁做技术决策
2. 开发节奏被打断，等待用户回复期间无法推进
3. 决策标准不统一，类似情况可能做出不同决策

**现在的做法**：建立标准化决策方法论，agent自行评估并执行，只在以下情况才需要用户决策：
- 涉及核心体验方向的重大选择（如UI布局大改、核心机制变更）
- 涉及删除或大幅改动已有功能
- 涉及与用户已确认原则冲突的设计
- 方法论无法覆盖的特殊情况

---

## 二、六维决策模型

每个待办任务按以下6个维度评分（1-5分，5分最高），然后计算综合优先级。

### 维度1：阻塞性（Blocker）

**定义**：这个任务是否阻塞了其他任务的推进？

| 评分 | 标准 |
|------|------|
| 5 | 阻塞了3个以上其他任务，或阻塞了当前版本发布 |
| 4 | 阻塞了1-2个其他高优先级任务 |
| 3 | 不阻塞其他任务，但延迟会影响后续效率 |
| 2 | 完全不阻塞其他任务，只是锦上添花 |
| 1 | 做了反而可能阻塞其他任务（如引入不稳定变更） |

### 维度2：用户价值（User Value）

**定义**：这个任务能给玩家/用户带来什么体验提升？

| 评分 | 标准 |
|------|------|
| 5 | 核心体验提升，玩家能明显感受到（如战斗手感优化、核心剧情补全） |
| 4 | 重要体验提升，多数玩家会受益（如NPC对话补全、系统优化） |
| 3 | 一般体验提升，部分玩家会注意到（如UI微调、文案优化） |
| 2 | 轻微体验提升，只有细心玩家会注意到（如动画细节、音效） |
| 1 | 几乎无体验提升，纯技术优化（如代码重构、注释补充） |

### 维度3：技术债务（Tech Debt）

**定义**：不做这个任务，会不会导致后续更难维护或更难扩展？

| 评分 | 标准 |
|------|------|
| 5 | 严重技术债务，不还会导致后续开发寸步难行（如架构缺陷、数据格式混乱） |
| 4 | 明显技术债务，不还会显著增加后续工作量（如重复代码、缺乏抽象） |
| 3 | 轻微技术债务，不还会偶尔造成困扰（如命名不规范、缺少文档） |
| 2 | 几乎无技术债务，只是代码风格问题 |
| 1 | 做了反而可能增加技术债务（如过度设计、过早优化） |

### 维度4：完成度（Completeness）

**定义**：当前任务的核心功能是否已经完成？

| 评分 | 标准 |
|------|------|
| 5 | 核心功能100%完成，只剩边缘case和打磨 |
| 4 | 核心功能80%完成，主要流程可跑通 |
| 3 | 核心功能50%完成，主要流程有断点 |
| 2 | 核心功能20%完成，只有框架 |
| 1 | 完全没开始 |

**决策含义**：
- 完成度≥4（核心已完成）→ 可以考虑切换任务，剩余优化可后续增量进行
- 完成度≤3（核心未完成）→ 应继续完成，避免留下半拉子工程

### 维度5：风险（Risk）

**定义**：继续做这个任务的风险是什么？

| 评分 | 标准 |
|------|------|
| 5 | 风险极高，可能引入严重bug或破坏现有功能（如核心架构重构） |
| 4 | 风险较高，可能影响多个系统（如战斗系统大改） |
| 3 | 风险中等，可能影响单个系统（如新增功能） |
| 2 | 风险较低，只影响非核心功能（如UI调整） |
| 1 | 几乎无风险，纯增量或纯数据修改 |

**决策含义**：
- 风险≥4 → 谨慎推进，最好先做充分测试或分阶段实施
- 风险≤2 → 可以大胆推进

### 维度6：依赖关系（Dependency）

**定义**：其他任务是否依赖这个任务的完成？或者这个任务是否依赖其他任务？

| 评分 | 标准 |
|------|------|
| 5 | 被3个以上其他任务依赖，是关键路径 |
| 4 | 被1-2个高优先级任务依赖 |
| 3 | 被低优先级任务依赖，或依赖其他低优先级任务 |
| 2 | 无依赖关系，完全独立 |
| 1 | 依赖其他未完成的高优先级任务（应先做被依赖的任务） |

## 三、综合优先级计算

### 计算公式

```
综合优先级 = 阻塞性×0.25 + 用户价值×0.25 + 技术债务×0.15 + 完成度×0.10 + (6-风险)×0.10 + 依赖关系×0.15
```

**权重说明**：
- 阻塞性和用户价值权重最高（各25%），因为这两个直接影响项目推进和玩家体验
- 技术债务和依赖关系次之（各15%），因为这两个影响长期可维护性
- 完成度和风险权重较低（各10%），作为辅助判断

### 优先级分级

| 综合优先级 | 等级 | 决策 |
|-----------|------|------|
| ≥4.0 | P0 紧急 | 立即执行，其他任务让路 |
| 3.0-3.9 | P1 高 | 优先执行，除非有P0任务 |
| 2.0-2.9 | P2 中 | 按计划执行，可灵活调整 |
| <2.0 | P3 低 | 有空再做，或攒一波一起做 |

## 四、特殊决策规则

### 规则1：核心功能未完成不切换

**条件**：当前任务完成度≤3（核心功能未完成）
**决策**：继续完成当前任务，不切换
**例外**：当前任务被更高优先级任务阻塞，或发现当前任务方向错误需要重新评估

### 规则2：版本发布前必须收尾

**条件**：距离版本发布还剩核心功能已完成
**决策**：先完成必要收尾（测试/文档/版本号），再切换到下一个大任务
**必要收尾清单**：
- 自动化测试全部通过
- 手动冒烟测试通过（核心流程可跑通）
- CHANGELOG更新
- TODO更新
- 版本号更新（AGENTS.md/ui.js）
- README更新（如有新功能）

### 规则3：技术债务超过阈值必须还

**条件**：某个任务的技术债务评分≥4，且已存在超过2个版本
**决策**：必须在当前版本或下一个版本安排偿还
**原因**：技术债务越拖越难还，会导致后续开发效率持续下降

### 规则4：用户明确要求的任务优先

**条件**：用户在最近3轮对话中明确要求做某个任务
**决策**：该任务的用户价值评分自动+1（最高5分）
**原因**：用户的明确需求是最高优先级

### 规则5：相似任务批量处理

**条件**：有多个相似的小任务（如多个NPC对话补全、多个文案修改）
**决策**：批量处理，不要做一个切一个
**原因**：上下文切换成本高，批量处理效率更高

## 五、决策记录与迭代

### 决策记录格式

每次重大决策（切换任务/优先级调整/范围变更）都要记录：

```markdown
### 决策记录：[决策标题]
- **日期**：YYYY-MM-DD
- **背景**：面临什么抉择
- **备选方案**：A/B/C...
- **六维评分**：
  - 方案A：阻塞性X/用户价值X/技术债务X/完成度X/风险X/依赖关系X = 综合X.X
  - 方案B：...
- **决策**：选择方案X
- **理由**：为什么选这个
- **后续验证**：如何验证这个决策是对的
```

### 方法论迭代

每5个版本后，回顾过去的决策记录：
- 哪些决策做对了？为什么？
- 哪些决策做错了？为什么？
- 六维评分的权重是否需要调整？
- 是否需要新增维度？
- 是否需要新增特殊规则？

迭代结果更新到本文档中。

## 六、当前决策示例

### 背景

v3.14.0 NPC分层与自然触发系统重构的核心功能已完成并通过测试（130通过/0失败）。面临抉择：
- **方案A**：继续做v3.14.0的后续优化（UI层2/环境台词补充/时间事件触发/activeStages精细调整/手动冒烟测试/文档同步）
- **方案B**：切换到博城篇小说拆解（第11-120章），这是用户明确要求的"把博城篇做完美"的基础
- **方案C**：先做v3.14.0必要收尾，然后切换到博城篇拆解

### 六维评分

**方案A（继续v3.14.0优化）**：
- 阻塞性：2（不阻塞其他任务，但手动冒烟测试和文档同步是版本发布必要步骤）
- 用户价值：3（环境台词补充提升世界鲜活度，但核心机制已完成）
- 技术债务：2（核心架构已完成，后续优化是增量）
- 完成度：5（核心功能100%完成）
- 风险：1（几乎无风险）
- 依赖关系：2（无强依赖）
- **综合**：2×0.25 + 3×0.25 + 2×0.15 + 5×0.10 + (6-1)×0.10 + 2×0.15 = 0.5+0.75+0.3+0.5+0.5+0.3 = **2.85（P2）**

**方案B（直接切换到博城篇拆解）**：
- 阻塞性：4（博城篇内容完善依赖拆解结果）
- 用户价值：5（用户明确要求"把博城篇做完美"，拆解是基础）
- 技术债务：1（无技术债务）
- 完成度：1（只完成了第1-10章，还有110章）
- 风险：2（风险较低，方法论已建立）
- 依赖关系：5（被博城篇内容完善依赖，是关键路径）
- **综合**：4×0.25 + 5×0.25 + 1×0.15 + 1×0.10 + (6-2)×0.10 + 5×0.15 = 1.0+1.25+0.15+0.1+0.4+0.75 = **3.65（P1）**

**方案C（先收尾再切换）**：
- 阻塞性：4（收尾是版本发布必要步骤，不做会留下半拉子版本）
- 用户价值：4（收尾保证版本质量，拆解是用户明确需求）
- 技术债务：2（收尾避免技术债务）
- 完成度：4（收尾后v3.14.0完成度100%）
- 风险：1（几乎无风险）
- 依赖关系：4（博城篇内容完善依赖拆解，拆解不依赖v3.14.0优化）
- **综合**：4×0.25 + 4×0.25 + 2×0.15 + 4×0.10 + (6-1)×0.10 + 4×0.15 = 1.0+1.0+0.3+0.4+0.5+0.6 = **3.8（P1）**

### 决策

**选择方案C：先做v3.14.0必要收尾，然后切换到博城篇拆解。**

**理由**：
1. 方案C综合优先级最高（3.8），兼顾了版本质量和用户需求
2. v3.14.0核心功能已完成（完成度5），符合"核心功能未完成不切换"规则的反面——可以切换
3. 但版本发布前必须收尾（规则2），所以先做必要收尾
4. 博城篇拆解是用户明确要求（规则4），且是关键路径（依赖关系5），优先级高
5. v3.14.0的后续优化（环境台词补充等）可以在博城篇内容完善过程中同步进行，因为补全NPC对话时自然会涉及

**必要收尾清单**：
1. CHANGELOG更新（v3.14.0条目）
2. TODO更新（v3.14.0标记完成，新增博城篇拆解任务）
3. 版本号更新（AGENTS.md/ui.js）
4. 设计文档已完成（v3.14.0设计文档已写）

**后续验证**：
- v3.14.0收尾后，版本是否稳定可用？
- 博城篇拆解进度是否按计划推进？
- v3.14.0的后续优化是否在博城篇内容完善中同步完成？

## 七、总结

本方法论的核心是：
1. **标准化**：用六维评分代替主观判断，决策可解释
2. **可复用**：类似情况用同样的标准，决策一致
3. **可迭代**：每5个版本回顾决策记录，持续优化
4. **少打扰用户**：只有重大方向选择才需要用户决策，日常抉择agent自行处理

**agent的职责**：
- 遇到抉择时，先用本方法论评估
- 评估后自行执行，不需要问用户
- 记录决策过程和结果
- 每5个版本回顾并优化方法论

**用户的职责**：
- 明确核心方向和原则（如"把博城篇做完美"）
- 在重大方向选择时做最终决策
- 对方法论本身提出改进意见
