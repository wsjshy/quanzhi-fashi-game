- Debug是测试基础设施，不是可选便利功能

### 7.2 完整测试流程

1. **设计阶段**：写设计文档→包含测试要点→写核心测试用例
2. **开发阶段**：实施开发→同步开发Debug功能→单元测试
3. **完成后**：自动化测试（L1/L2/L3）→冒烟测试→黑盒测试（功能+体验）
4. **修复后**：修bug→回归测试→确认修复
5. **发布前**：完整测试用例逐项验证→体验测试→文档同步
6. **发布后**：版本反思会→测试方法论回顾→自迭代

### 7.3 Debug功能扩展规范

- 每个新系统必须有对应Debug功能
- Debug功能包括：快速触发事件/跳过阶段/调整数值/查看状态
- Debug面板分类：角色/物品/传送/剧情/战斗/天赋/跳过
- 新NPC/新地点/新任务要能在debug中快速访问
- debug面板本身也要测试，不能坏了

### 7.4 黑盒测试标准化流程

1. 用debug快速进入对应阶段
2. 按测试用例逐项验证
3. 功能测试：正常流程/边界条件/异常情况
4. 体验测试：节奏/压力/自由度/代入感
5. 记录问题→分级（P0阻塞/P1重要/P2次要）
6. 修复bug→回归验证
7. 输出测试报告

### 7.5 测试方法论自迭代机制

- 每版本回顾：测试用例覆盖率/发现的bug模式/测试效率
- 每5版本评审：测试方法论改进/新测试方法/工具升级
- 新bug模式立即沉淀：记录到开发踩坑记录+测试用例补充
- 测试用例库持续积累：每个新系统的测试用例都保存到测试用例文档

## 八、风险与应对

### 8.1 工作量风险

**风险**：博城篇内容完善计划涉及约50个P0系统，预估需要18个版本（v3.15.0 - v3.32.0），工作量巨大。

**应对**：
- 按阶段实施，每阶段2-4个版本
- 每版本聚焦1-2个核心系统，不贪多
- 优先做用户最关注的博城灾难线和救援叶心夏线
- 可复用现有系统（大事件系统/对话树/任务系统），不重复造轮子
- 纯设定展示用文本带过，不造系统

### 8.2 游戏负担风险

**风险**：内容增加可能导致游戏负担过重，玩家发现很多NPC等着对话，无形中有种压力。

**应对**：
- 严格遵循v3.14.0 NPC分层与自然触发系统
- 核心NPC密度控制（同时最多3个"新对话"提示）
- 环境对话系统（进入地点时背景NPC自动说台词，不需要玩家点击）
- 对话可以有，但不要全是对话，有些对话可以随着剧情自然出现
- 背景NPC点击只显示随机台词，不进入对话树
- 定期评估游戏负担，发现问题立即优化

### 8.3 玩家视角风险

**风险**：内容增加可能不自觉地从莫凡视角介入，忘记玩家是另外的视角。

**应对**：
- 严格遵循核心原则第一条：玩家有自己的人生，不对标莫凡
- 贴合小说原文主要是贴合各种设定，玩家不是莫凡
- 莫凡是背景中实力强劲的NPC
- 玩家通过选择创造新剧情可能性，不脱离原著但不被原著束缚
- 每个新系统设计时必须明确：玩家如何介入？玩家的选择是什么？
- 定期审视，发现莫凡视角问题立即纠正

### 8.4 设定一致性风险

**风险**：内容增加可能导致设定不一致，与小说原著有偏差。

**应对**：
- 涉及小说内容必须先读原文验证（全职法师.txt）
- 不凭记忆或已有拆解编造设定
- 非原著内容必须标记isCanon: false + canonNote
- 新增数据前必须先检索，确认ID和名称不重复
- 定期做原文回归校准
- 博城篇原文回归校准报告持续更新

### 8.5 测试质量风险

**风险**：内容增加可能导致测试覆盖不足，bug遗漏。

**应对**：
- 严格遵循测试方法论v2.0
- 测试左移：开发前写好测试用例
- 每个新系统同步开发Debug功能
- 自动化测试+黑盒测试双重保障
- 每版本发布前完整测试用例逐项验证
- 测试方法论自迭代，持续改进

## 九、自迭代机制

### 9.1 每版本反思会（30分钟）

- 做得好的/做得不好的
- 方法论反馈
- 玩家体验
- 下版本重点
- 记录到docs/version-reflection/vX.Y.Z_反思.md

### 9.2 每5版本健康度审计（1小时）

- 文档审计
- 代码审计
- 方法论审计
- 创新审计
- 发现问题立即创建任务到TODO
- 记录到docs/version-reflection/健康度审计_vX.Y.Z.md

### 9.3 每10版本方法论评审会（2小时，需用户确认）

- 回顾使用情况
- 评审改进提案
- 检查创新空间
- 决定方法论保留/修改/废弃/新增
- 向用户汇报并确认
- 执行方法论更新
- 记录到docs/version-reflection/方法论评审_vX.Y.Z.md

### 9.4 任务优先级决策方法论

- 六维评分模型（阻塞性25%/用户价值25%/技术债务15%/完成度10%/风险10%/依赖关系15%）
- 5条特殊决策规则
- agent自行决策，不每次都问用户
- 详见docs/任务优先级与决策方法论.md
