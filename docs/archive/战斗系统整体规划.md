# 战斗系统整体规划（小说驱动式开发）

## 一、核心思想

### 小说驱动开发
**从小说里发现什么，就实现什么**。不是先把所有机制都做完，而是随着小说拆解逐步扩充。

- 看到一个新妖魔 → 就加一个妖魔
- 看到一个新天赋 → 能复用现有效果就复用，不能就新增效果类型
- 看到一个新魔法 → 就加一个魔法
- 看到一个新机制 → 就实现一个新机制

**不固定数量，不设上限，跟着小说走。**

---

## 二、三层架构设计

### 第一层：基础框架层（最稳定，改动最少）
一旦搭好，很少改动，是所有内容的基础。

**包含**：
- 战斗回合逻辑
- 伤害计算基础
- 状态效果基础框架
- 天赋效果基础框架
- AI决策基础框架
- 事件系统

**特点**：
- 稳定，很少改动
- 提供基础接口
- 所有上层内容都基于这一层

---

### 第二层：效果类型层（逐步扩充）
随着小说拆解，不断发现新的效果类型，逐步添加。

**效果类型库**（持续扩充中）：

| 类别 | 效果类型 | 说明 | 状态 |
|------|---------|------|------|
| 基础属性 | passive_bonus | 被动属性加成（攻击/防御/速度/HP/闪避） | ✅ 已实现 |
| 伤害相关 | damage_reduction | 伤害减免（物理/魔法） | ✅ 已实现 |
| 伤害相关 | damage_reflect | 伤害反弹 | ✅ 已实现 |
| 攻击相关 | first_strike | 首次攻击特效（必暴击/伤害加成） | ✅ 已实现 |
| 攻击相关 | bleed_on_hit | 攻击造成流血 | ✅ 已实现 |
| 防御相关 | weakness | 弱点伤害（特定属性伤害增加） | ✅ 已实现 |
| 防御相关 | control_immune | 控制免疫 | ✅ 已实现 |
| 回复相关 | regen | 回合结束恢复HP | ✅ 已实现 |
| 动态效果 | blood_rage | 血怒（血量越低攻击越高） | ✅ 已实现 |
| ... | ... | （随着小说拆解继续添加） | 🔄 持续扩充 |

**特点**：
- 模块化新增
- 每个新效果类型是独立的
- 不影响现有效果
- 可以复用

---

### 第三层：内容数据层（最灵活，扩充最快）
纯数据，新增只需要加数据，不需要改代码。

**包含**：
- 具体的妖魔数据
- 具体的技能数据
- 具体的天赋配置
- 具体的物品数据
- 具体的NPC数据
- 具体的地点数据

**特点**：
- 纯数据
- 新增只加数据
- 不需要改代码
- 扩充最快

---

## 三、开发流程

### 标准流程

```
拆解小说章节
    ↓
发现新内容（妖魔/魔法/天赋/机制）
    ↓
检查现有效果类型能不能实现？
    ├─ 能 → 直接加数据 ✅
    └─ 不能 → 新增效果类型（写代码）→ 然后加数据
```

### 详细步骤

#### 第一步：拆解小说
阅读小说章节，标记出：
- 🐺 新妖魔出现
- ✨ 新魔法释放
- 🎯 特殊能力/天赋
- 👤 新人物
- 📍 新地点
- 🎁 新物品

#### 第二步：评估实现方式
对于每个新发现的内容：
1. 现有的效果类型能不能实现？
2. 如果能 → 直接配置数据
3. 如果不能 → 需要新增什么效果类型？

#### 第三步：实现
- **数据层面**：添加到对应的数据文件
- **代码层面**：如果需要新效果类型，新增效果模块，注册到效果注册表

#### 第四步：测试
- 测试新内容是否正常工作
- 测试是否影响现有内容
- 调整数值平衡

#### 第五步：标记来源
- **小说原著内容**：默认 `isCanon: true`，description尽量引用小说原文
- **非原著/游戏原创内容**：必须标记 `isCanon: false` 和 `canonNote: "非原著，游戏原创"`
- **后续新增严格按小说**：不要自己编妖魔或技能，从小说原文提取

```javascript
// 小说原著妖魔
one_eye_wolf: {
  id: "one_eye_wolf",
  name: "独眼魔狼",
  // isCanon默认为true，不需要写
}

// 非原著妖魔（游戏原创）
skeleton_warrior: {
  id: "skeleton_warrior",
  name: "骷髅战士",
  isCanon: false,
  canonNote: "非原著妖魔，游戏原创",
}
```

## 四、代码组织方式

### 效果注册表模式
所有效果类型都注册到一个表里，新增效果只需要注册，不需要改主逻辑。

```javascript
// 天赋效果注册表
const TraitEffectRegistry = {
    // 基础效果
    'passive_bonus': handlePassiveBonus,
    'damage_reduction': handleDamageReduction,
    'first_strike': handleFirstStrike,
    'weakness': handleWeakness,
    
    // 持续扩充...
    'regen': handleRegen,
    'bleed_on_hit': handleBleedOnHit,
    'damage_reflect': handleDamageReflect,
    'blood_rage': handleBloodRage,
    'control_immune': handleControlImmune,
    
    // 未来新增的效果类型...
}

// 使用效果
function applyTraitEffect(trait, unit, params) {
    const handler = TraitEffectRegistry[trait.type];
    if (handler) {
        handler(trait.effects, unit, params);
    }
}
```

**好处**：
- 新增效果类型只需要加一个注册项
- 不影响现有效果
- 每个效果独立，容易调试
- 可以复用

---

### 妖魔天赋的实现方式

每个妖魔的天赋是**数据**，但天赋的**效果类型**是代码：

```javascript
// 妖魔天赋配置（数据）
"one_eye_wolf": {
    traits: [
        {
            id: "fierce",
            name: "凶猛",
            type: "passive_bonus",    // 效果类型（代码实现）
            effects: { attackBonus: 0.2 }  // 参数（数据配置）
        },
        {
            id: "shadow_assault",
            name: "暗影突袭",
            type: "first_strike",     // 效果类型
            effects: { crit: true, damageBonus: 0.5 }  // 参数
        }
    ]
}
```

**关键原则**：
- 相同效果类型的天赋，可以用不同参数配置
- 比如"被动加成"可以加攻击、加防御、加速度...
- 新的天赋如果能用现有效果类型实现，就只加数据
- 实现不了的，就新增效果类型

## 六、开发原则

### 原则一：小说驱动
- 从小说里发现什么，就实现什么
- 不凭空想象机制
- 所有内容都要有原著依据

### 原则二：数据优先
- 能用数据实现的，就用数据实现
- 尽量复用现有效果类型
- 减少不必要的代码改动

### 原则三：模块化新增
- 新效果类型做成独立模块
- 通过注册表统一管理
- 新增不破坏现有逻辑

### 原则四：逐步完善
- 不追求一步到位
- 边拆解边完善
- 先有后优

### 原则五：可复用
- 每个效果类型都设计成可复用的
- 一个效果类型可以用在多个地方
- 避免重复代码

## 八、检查清单

每次新增内容时，检查：

### 数据层面
- [ ] 能用现有效果类型实现吗？
- [ ] 数据结构和现有内容一致吗？
- [ ] ID命名规范吗？
- [ ] 符合原著设定吗？
- [ ] 数值合理吗？

### 代码层面（如果需要新增效果类型）
- [ ] 新效果类型是独立模块吗？
- [ ] 有没有注册到效果注册表？
- [ ] 会不会影响现有效果？
- [ ] 可以复用吗？
- [ ] 有测试吗？

## 九、总结

### 核心思想
**小说驱动，看到一个加一个**。不固定数量，不设上限，跟着小说走。

### 三层架构
1. **基础框架层** - 稳定，改动少
2. **效果类型层** - 逐步扩充，模块化新增
3. **内容数据层** - 最灵活，扩充最快

### 开发流程
拆解小说 → 发现新内容 → 评估实现方式 → 数据/代码实现 → 测试

### 好处
- ✅ 内容有原著依据，不凭空想象
- ✅ 新增内容快，数据优先
- ✅ 代码改动可控，模块化新增
- ✅ 可持续发展，可以一直扩充
- ✅ 边做边完善，不追求一步到位

---

**记住：我们不是在做一个固定内容的游戏，而是在做一个可以随着小说拆解不断成长的游戏。**
