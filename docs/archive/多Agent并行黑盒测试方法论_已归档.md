## 一、核心思路

### 1.1 为什么用多Agent并行测试

**传统测试的问题**：
- 开发者自己测，容易陷入思维定式，测不出自己写的bug
- 单人测试速度慢，覆盖不全
- 从开发者视角测，不是从玩家视角测

**多Agent黑盒测试的优势**：
- 纯玩家视角，不知道代码实现，发现的问题更真实
- 并行测试，多个Agent同时测不同内容，效率翻倍
- 7x24小时不间断，不知疲倦
- 每个Agent都是独立的，不会互相影响
- 测试过程详细记录，每一步操作都有日志

### 1.2 黑盒测试原则

**绝对不能告诉Agent的信息**：
- ❌ 代码实现细节
- ❌ 修复了什么bug
- ❌ 新增了什么功能
- ❌ 数值公式
- ❌ 设计思路
- ❌ 任何内部信息

**只告诉Agent的信息**：
- ✅ 这是个什么游戏
- ✅ 基本操作方式
- ✅ 你的任务是玩游戏，找bug，记录体验
- ✅ 发现任何不对劲的地方都记录下来

**为什么要纯黑盒**：
- 玩家不知道代码怎么写的，他们遇到问题就是真问题
- 如果告诉Agent"我修了XXbug"，Agent会特意去测那个点，而不是自然游玩中发现
- 黑盒发现的bug优先级更高，因为真实玩家也会遇到

## 二、多Agent分工策略

### 2.1 按测试方向分工

建议同时开 3-5 个Agent，每个负责不同方向：

| Agent角色 | 测试重点 | 目标 |
|-----------|----------|------|
| **新手体验官** | 从零开始，完整体验新手流程 | 发现新手引导问题、前期bug、入门难度问题 |
| **战斗狂人** | 专注战斗系统，打各种怪，试各种技能 | 发现战斗bug、平衡问题、技能bug |
| **探索家** | 跑遍所有地图，做所有任务，和所有NPC对话 | 发现内容bug、任务bug、NPC对话bug |
| **经济学者** | 专注商店、装备、强化、赚钱、花钱 | 发现经济系统bug、数值平衡问题 |
| **极限测试员** | 故意作死，试各种边界情况 | 发现崩溃bug、异常状态、边界条件问题 |

### 2.2 按进度分工

也可以按游戏进度分工：

| Agent | 游戏阶段 | 测试重点 |
|-------|----------|----------|
| Agent A | 前期（1-5级） | 新手体验、前期平衡、入门引导 |
| Agent B | 中期（5-10级） | 中期系统、装备、技能、任务 |
| Agent C | 后期（10级+） | 后期内容、大事件、高级系统 |

### 2.3 并行数量建议

- **最少2个**：一个测新手，一个测深度
- **推荐3-4个**：覆盖主要玩法方向
- **最多5-6个**：太多了bug反馈处理不过来
- **不要超过8个**：边际效益递减，管理成本上升

## 三、Agent测试指令模板

### 3.1 通用指令模板

```
你的任务是：作为一个普通玩家，从头开始玩这个游戏，记录你的游玩过程，发现所有bug和体验问题。

重要：你是纯玩家，不知道游戏是怎么做的，也不知道有什么功能。你就像第一次玩这个游戏的玩家一样，自然地去玩，去探索，去尝试。

游戏路径：[游戏路径]

你需要做的：
1. 自然游玩，想怎么玩就怎么玩，不要刻意按某个路线
2. 详细记录每一步操作和结果（点了什么按钮，发生了什么）
3. 发现任何bug都记录下来（包括：现象、复现步骤、严重程度）
4. 体验不好的地方也记录下来（比如：不知道该做什么、某个按钮太难找、提示不清楚）
5. 平衡问题也记录（比如：某个怪太强、某个技能太弱、钱太多/太少）
6. 随机性的结果也要记录（比如：伤害数值、掉落物品、事件触发）

bug严重程度分级：
- 严重：游戏崩溃、存档丢失、核心功能无法使用
- 较重：重要功能bug、资源异常、进度卡住
- 中等：体验问题、显示错误、提示不清
- 轻微：文字错误、排版问题、小瑕疵

玩到你觉得当前内容都体验得差不多了，或者遇到严重bug无法继续，就结束。

最后把你的所有记录整理成一份测试报告，包括：
- 游玩进度（等级、天数、解锁了什么）
- 发现的bug列表（按严重程度排序）
- 体验问题列表
- 平衡问题列表
- 整体评价和建议
```

### 3.2 专项测试指令模板

**战斗专项测试**：
```
你的任务是：专注测试游戏的战斗系统。

你需要：
1. 尽量多打不同的敌人
2. 尝试所有可用的技能
3. 测试各种战斗状态（buff/debuff/眩晕/燃烧等）
4. 测试战斗道具
5. 测试逃跑、防御等战斗操作
6. 测试不同元素系的克制关系

重点关注：
- 战斗会不会卡住、崩溃
- 伤害数值对不对
- 技能效果有没有问题
- 状态效果有没有问题
- 战斗流程顺不顺畅
```

**经济专项测试**：
```
你的任务是：专注测试游戏的经济系统。

你需要：
1. 尝试各种赚钱方式
2. 尝试各种花钱方式
3. 测试商店、装备、强化等系统
4. 看看钱够不够花，或者钱是不是太多了
5. 物品价格合不合理

重点关注：
- 有没有刷钱bug
- 商店物品能不能正常买/卖
- 装备强化有没有问题
- 经济节奏好不好
```

## 四、bug反馈与迭代流程

### 4.1 bug反馈模板

每个Agent反馈的bug应该包含：

```
【Bug编号】bug-001
【严重程度】严重/较重/中等/轻微
【所属系统】战斗/任务/UI/存档/经济/其他
【Bug标题】一句话描述问题
【复现步骤】
1. ...
2. ...
3. ...
【预期结果】应该发生什么
【实际结果】实际发生了什么
【截图/日志】如果有的话
【出现频率】每次都出现/偶尔出现/只出现过一次
【备注】其他相关信息
```

### 4.2 迭代循环

**理想的开发-测试循环**：

```
第一轮：
  → 开发完成初版
  → 启动3-4个Agent并行测试
  → 收集所有bug和反馈
  → 按优先级排序

第二轮：
  → 修复P0/P1级bug
  → 做重要的体验优化
  → 重新启动Agent测试（验证修复+继续深入）
  → 收集新的bug和反馈

第三轮：
  → 修复剩余bug
  → 继续优化
  → Agent继续测试更深的内容
  → ...

第N轮：
  → bug数量降到可接受水平
  → 体验问题基本解决
  → 测试通过，可以发布
```

### 4.3 并行配合要点

**开发者（主Agent）做的事**：
- 修复bug
- 做优化
- 新增内容
- 整理和分类bug反馈
- 决定优先级

**测试员（子Agent）做的事**：
- 玩游戏
- 发现bug
- 记录体验问题
- 验证修复（下一轮测试时自然验证）

**配合方式**：
- 测试和开发并行进行，不要等
- 一批bug修完就丢回去重新测
- 测试中发现的新bug随时加入待修列表
- 形成"测试→修复→再测试→再修复"的快速迭代循环

## 五、效率提升技巧

### 5.1 如何让Agent测的更深

**问题**：Agent玩到一定程度就停了，测不到后期内容。

**解决方案**：
1. **给存档**：提前准备好不同进度的存档，让Agent从不同进度开始测
2. **给目标**：给Agent一个明确的目标，比如"想办法升到10级"、"去XX地点探索"
3. **分段测试**：第一轮测前期，第二轮测中期，第三轮测后期
4. **提示**：如果Agent卡住了，可以给一点提示，但不要太多，保持黑盒

### 5.2 如何减少重复bug

**问题**：多个Agent发现同一个bug，重复反馈。

**解决方案**：
1. 每轮测试后整理bug列表，去重
2. 下一轮测试前不用告诉Agent修了什么，让他们自然验证
3. 如果同一个bug被多个Agent发现，说明优先级很高，要优先修

### 5.3 如何提高bug质量

**问题**：Agent反馈的bug太模糊，不知道怎么复现。

**解决方案**：
1. 要求Agent详细记录每一步操作
2. 要求Agent记录出现频率（每次都有/偶尔/只一次）
3. 重要的bug让多个Agent尝试复现
4. 开发者自己也要复现验证

### 5.4 如何平衡黑盒和效率

**问题**：纯黑盒的话，Agent可能会卡在很简单的问题上，浪费时间。

**解决方案**：
1. **基本操作可以教**：比如怎么打开背包、怎么战斗
2. **游戏内容不要教**：比如有什么技能、怎么升级快
3. **卡住时可以给小提示**：比如"试试去XX地方看看"，但不要太详细
4. **重点测试的地方可以引导**：比如"多试试战斗系统"，但不要说具体怎么试

## 六、适用场景

### 6.1 最适合的项目类型

- ✅ 游戏类项目（内容多，系统复杂，需要大量测试）
- ✅ 网页应用（交互多，流程复杂）
- ✅ 有用户界面的产品
- ✅ 迭代开发中的项目（需要持续测试）

### 6.2 不太适合的项目

- ❌ 纯算法/纯后端（没有UI，黑盒测不了）
- ❌ 非常简单的小工具（不值得开多个Agent）
- ❌ 需求还不明确的项目（先明确需求再测）

## 七、成本与收益

### 7.1 成本

- **时间成本**：每个Agent跑一轮大概几十分钟到几小时
- **Token成本**：详细记录的话，每个Agent消耗不少token
- **管理成本**：需要人整理bug、分配优先级、修复

### 7.2 收益

- **测试覆盖率**：比单人测试高很多
- **bug发现率**：黑盒测试能发现开发者想不到的bug
- **时间节省**：并行测试，几天的活一天干完
- **质量提升**：多轮迭代后，产品质量明显提升
- **体验优化**：从玩家视角出发，体验更真实

### 7.3 性价比评估

**什么时候值得用**：
- 项目有一定规模（不是小玩具）
- 有UI交互
- 需要保证质量
- 迭代开发，持续更新

**什么时候不值得用**：
- 太小的项目
- 一次性的，不会更新
- 纯后端/纯算法

## 八、实战经验总结

### 8.1 踩过的坑

1. **不要告诉Agent开发信息**：一说"我修了XXbug"，Agent就会特意去测那个点，不是自然游玩发现的，参考价值下降
2. **不要给太多指引**：指引太多就不是黑盒了，发现的问题都是你引导出来的
3. **不要只开一个Agent**：一个Agent测的太单一，多几个Agent视角更多元
4. **不要测一轮就完事**：第一轮只能发现表面问题，多轮迭代才能发现深层问题
5. **不要忽视体验问题**：bug要修，体验问题也要重视，很多时候体验问题比bug更影响玩家留存

### 8.2 成功经验

1. **详细记录很重要**：每一步操作都记录，复现bug就容易
2. **分级很重要**：严重bug优先修，轻微bug可以攒着一起改
3. **并行效率真的高**：3个Agent并行，相当于3倍测试速度
4. **黑盒发现的bug质量高**：都是真实玩家会遇到的问题
5. **迭代循环效果好**：一轮一轮测下来，质量提升很明显

### 8.3 未来可以探索的方向

1. **自动化测试+Agent测试结合**：自动化测回归，Agent测体验和新功能
2. **不同类型的Agent**：新手玩家、硬核玩家、休闲玩家，不同人设
3. **A/B测试**：两个版本同时给不同Agent测，对比哪个更好
4. **压力测试**：同时开很多个Agent，测服务器性能

---

## 结语

多Agent并行黑盒测试是一种非常高效的测试方法，特别适合游戏类、UI类项目。

核心就是：**让不懂代码的人（Agent）从玩家角度去玩，发现的问题就是真问题。多个一起上，效率翻倍。**

用好了，能大大提升产品质量，减少上线后的bug。
