# 可扩展架构设计与小说拆解方法论

## 一、核心设计原则

### 1.1 数据驱动原则
**所有游戏内容都应该是数据驱动的**，新增内容只需要添加数据，不需要修改代码。

✅ 好的设计：
- 新增一个妖魔：只需要在 `enemies.js` 里加一条数据
- 新增一个天赋：只需要在 `demon-traits.js` 里加一条数据
- 新增一个技能：只需要在 `skills.js` 里加一条数据

❌ 坏的设计：
- 新增一个妖魔要改好几处代码
- 新增一个天赋要在战斗逻辑里加 if-else

### 1.2 模块化原则
每个系统都是独立的模块，通过标准接口交互：
- 战斗系统：负责战斗逻辑
- 天赋系统：负责天赋效果
- 技能系统：负责技能释放
- 状态系统：负责状态效果

### 1.3 渐进式扩充原则
随着小说拆解逐步扩充内容：
- 第一卷（博城篇）：奴仆级妖魔、初阶魔法
- 第二卷：战将级妖魔、中阶魔法
- 第三卷：统领级妖魔、高阶魔法
- ...以此类推

## 三、可扩展架构设计

### 3.1 数据层架构

```
engine/data/
├── enemies.js          # 妖魔数据（可扩充）
├── skills.js           # 技能数据（可扩充）
├── demon-traits.js     # 妖魔天赋数据（可扩充）
├── status-effects.js   # 状态效果定义（可扩充）
├── items.js            # 物品数据（可扩充）
├── talents.js          # 玩家天赋数据（可扩充）
├── spirit-seeds.js     # 灵种数据（可扩充）
├── npcs.js             # NPC数据（可扩充）
├── locations.js        # 地点数据（可扩充）
├── events.js           # 事件数据（可扩充）
└── quests.js           # 任务数据（可扩充）
```

**所有数据文件都是键值对结构**：
```javascript
const DataXXX = {
    "id_1": { ...数据... },
    "id_2": { ...数据... },
    // 新增只需要在这里加
}
```

### 3.2 逻辑层架构

```
engine/
├── battle.js           # 战斗主逻辑
├── battle-ai.js        # 战斗AI
├── skill.js            # 技能系统
├── talent.js           # 天赋系统
├── spirit-seed.js      # 灵种系统
├── status-effect.js    # 状态效果系统
├── demon-trait.js      # 妖魔天赋系统
└── ...
```

### 3.3 效果注册表模式

**核心思想**：所有效果类型都注册到一个表里，新增效果类型只需要注册，不需要改主逻辑。

```javascript
// 效果注册表
const EffectRegistry = {
    // 伤害类
    'damage': handleDamage,
    'heal': handleHeal,
    'dot': handleDot,
    
    // 状态类
    'stun': handleStun,
    'slow': handleSlow,
    'buff': handleBuff,
    'debuff': handleDebuff,
    
    // 特殊类
    'interrupt': handleInterrupt,
    'summon': handleSummon,
    // 新增效果类型只需要在这里注册
}

// 使用效果
function applyEffect(effectType, params) {
    const handler = EffectRegistry[effectType];
    if (handler) {
        handler(params);
    }
}
```

## 四、小说拆解方法论

### 4.1 拆解目标
从小说文本中提取结构化的游戏数据，逐步扩充游戏内容。

### 4.2 拆解维度

#### 维度一：妖魔信息
**提取内容**：
- 基本信息：名字、种族、等级（奴仆/战将/统领/君主）
- 属性：HP、攻击、防御、速度
- 技能：种族技能、特殊能力
- 天赋：种族天赋、弱点
- 栖息地：出现地点
- 掉落：掉落物品、材料

**数据文件**：`enemies.js`、`demon-traits.js`、`skills.js`

**拆解模板**：
```javascript
"妖魔ID": {
    id: "妖魔ID",
    name: "妖魔名称",
    title: "奴仆级/战将级/统领级/君主级",
    description: "描述",
    elements: ["属性"],
    level: 等级,
    maxHp: HP,
    attack: 攻击,
    defense: 防御,
    speed: 速度,
    skills: ["技能ID1", "技能ID2"],
    aiType: "AI类型",
    enemyType: "demon",
    expReward: 经验,
    goldReward: 金币,
    dropItems: [...],
    locations: ["地点ID1", "地点ID2"]
}
```

---

#### 维度二：魔法/技能信息
**提取内容**：
- 基本信息：名字、系别、等级（初阶/中阶/高阶/超阶）
- 效果：伤害、治疗、buff、debuff
- 消耗：MP消耗、精神力消耗
- 引导时间：初阶瞬发，中阶2回合，高阶4回合
- 特殊效果：灼烧、冰冻、麻痹等

**数据文件**：`skills.js`

**拆解模板**：
```javascript
"技能ID": {
    id: "技能ID",
    name: "技能名称",
    element: "元素系",
    tier: "初阶/中阶/高阶",
    type: "damage/heal/buff/debuff",
    targetType: "single/aoe/self",
    baseDamage: 基础伤害,
    mpCost: MP消耗,
    castTime: 引导时间,
    cooldown: 冷却回合,
    description: "描述",
    effects: [
        { type: "damage", value: 100 },
        { type: "burn", chance: 0.3, duration: 3 }
    ]
}
```

---

#### 维度三：人物/NPC信息
**提取内容**：
- 基本信息：名字、身份、性格
- 属性：等级、系别、实力
- 关系：和主角的关系
- 功能：商店、任务、战斗等

**数据文件**：`npcs.js`

---

#### 维度四：地点信息
**提取内容**：
- 基本信息：名字、描述
- 类型：城市、荒野、秘境等
- 连接：相邻地点
- 功能：商店、修炼、战斗等
- 出现的妖魔：该地点的妖魔列表

**数据文件**：`locations.js`

---

#### 维度五：事件/剧情信息
**提取内容**：
- 基本信息：名字、描述
- 触发条件：等级、地点、时间等
- 选项：玩家选择
- 结果：不同选择的不同结果

**数据文件**：`events.js`

---

#### 维度六：物品/装备信息
**提取内容**：
- 基本信息：名字、类型、品质
- 效果：属性加成、特殊效果
- 获取方式：掉落、商店、任务等

**数据文件**：`items.js`

---

### 4.3 拆解流程

#### 第一步：通读章节，标记关键信息
阅读章节时，标记出：
- 🐺 妖魔出现
- ✨ 魔法释放
- 👤 人物出场
- 📍 地点描述
- 🎁 物品出现
- 🎬 重要事件

#### 第二步：提取结构化数据
根据标记的信息，提取成结构化的数据：
- 妖魔信息 → enemies.js 格式
- 魔法信息 → skills.js 格式
- 以此类推

#### 第三步：校验和补充
检查提取的数据：
- 是否完整？
- 是否符合原著设定？
- 数值是否合理？

#### 第四步：添加到游戏
把数据添加到对应的数据文件中：
- 不需要改代码
- 只需要加数据
- 测试一下是否正常工作

---

### 4.4 拆解优先级

#### P0（核心体验）
- 主要妖魔（每卷5-10种）
- 主要魔法（每系3-5个）
- 主要地点
- 主要NPC

#### P1（丰富内容）
- 次要妖魔
- 次要魔法
- 次要地点
- 支线任务

#### P2（细节填充）
- 背景人物
- 细节描述
- 彩蛋内容

## 五、版本规划与扩充节奏

### 5.1 按卷扩充

| 卷数 | 内容 | 新增妖魔 | 新增魔法 | 新增地点 |
|------|------|---------|---------|---------|
| 第一卷 | 博城篇 | 10-15种（奴仆级） | 10个初阶 | 5-8个 |
| 第二卷 | 魔都篇 | +10种（战将级） | +10个中阶 | +5-8个 |
| 第三卷 | 古都篇 | +10种（统领级） | +10个高阶 | +5-8个 |
| ... | ... | ... | ... | ... |

### 5.2 扩充原则
1. **先有后优** - 先把内容加进去，再慢慢优化
2. **数据驱动** - 所有内容都是数据，方便后续调整
3. **逐步深入** - 先基础信息，再细节填充
4. **保持一致** - 同一类内容用同样的结构

## 六、可扩展性检查清单

每次新增内容时，检查：

### 数据层
- [ ] 新增内容只需要加数据，不需要改代码吗？
- [ ] 数据结构和现有内容一致吗？
- [ ] ID命名规范吗？

### 逻辑层
- [ ] 新的效果类型有统一的处理方式吗？
- [ ] 可以通过注册的方式添加新效果吗？
- [ ] 主逻辑不需要修改吗？

### 内容层
- [ ] 符合原著设定吗？
- [ ] 数值平衡吗？
- [ ] 描述准确吗？

## 七、总结

### 核心思想
1. **数据驱动** - 内容和逻辑分离
2. **模块化** - 每个系统独立
3. **注册表模式** - 新增类型通过注册
4. **渐进式扩充** - 随着小说拆解逐步添加

### 好处
- ✅ 新增内容快 - 只需要加数据
- ✅ 维护容易 - 改数据不需要改代码
- ✅ 不容易出bug - 核心逻辑稳定
- ✅ 可以并行 - 多人可以同时拆解不同内容
- ✅ 可持续 - 可以一直扩充到小说完结
